## Design decisions (keep consistent when resuming)

- **batch-service** (new; MVC + plain JDBC, schema `batch`). OpenAI-compatible routes through the gateway's API-key chain: `POST /v1/files` (multipart `file` + `purpose=batch`), `GET /v1/files/{id}`, `GET /v1/files/{id}/content`, `DELETE /v1/files/{id}`, `POST /v1/batches`, `GET /v1/batches/{id}`, `POST /v1/batches/{id}/cancel`. Everything scoped to the caller's organization (another org's id → 404). No library: no Java caller. List endpoints and `metadata`: later.
- **Files in Postgres `bytea`** (ponytail: object storage when files outgrow the gateway's 4 MB `/v1` body cap or hosting is decided). Content is customer data: deleted on `DELETE`, expires 30 days after upload (hourly job), never logged.
- **Create validates synchronously** (400 instead of OpenAI's async `validating` → `failed`): JSONL, 1–50,000 lines, each `{custom_id (unique), method POST, url = endpoint, body {model, …}}`, one model for all lines, endpoint `/v1/chat/completions` only, `completion_window` `24h`. Lines are copied into `batch_line` (body with `stream: false`), the batch starts `in_progress` at once.
- **Worker**: `carmona.batch.workers` virtual threads; each claims one pending line of an in-progress, unexpired batch (oldest batch first) `FOR UPDATE SKIP LOCKED` and keeps the row lock for the call: the lock is the lease, so a crash re-dispatches the line, which still bills once (below). Calls inference-service directly with the batch's identity headers plus `batch-line`. 200 → done; 429/402/503 → roll back, sleep `retry-after-ms` (≤ 5 s); other 4xx → failed with the engine's answer; 5xx or no answer → attempt + 1, failed after 3.
- **Finisher** (every 2 s): in-progress batch with no pending line → `completed`; `cancelling` → unlocked pending lines dropped, `cancelled` when none is left; past `expires_at` → unlocked pending lines failed `batch_expired`, `expired` when none is left. Finalizing writes the output file (done lines, input order, OpenAI's line shape) and the error file (failed lines), stores the counts and deletes the lines, in one transaction. Counts of a running batch are counted on read.
- **inference-service** reads `batch-line: {batchId} {line} {batchCreatedAt}` (internal only; the gateway strips it from clients, or a client could buy sync answers at batch prices). For a batch line: vLLM priority 30; no rate buckets (the worker and the cap pace it); `no_credit:{org}` checked here because internal calls never pass the gateway's 402 (Valkey error → 503 so the worker backs off); admitted only while the model's in-flight count is under the trial share (`max(1, C/2)`), and not counted against the organization's own cap; usage event `mode=batch`, `event_id` = name-based UUID of (batch, line) (`UUID.nameUUIDFromBytes`, v3, stdlib, instead of v5), `started_at` = the batch's creation time, so a re-dispatched line hits the same primary key in usage-service and bills once. Only a batch line's `ok` run is reported: a failed or cut-short run would take the event id before the re-run that answered.
- **Batch prices** half of sync (OpenAI's batch discount), seeded by a billing-service migration that switches the future-only trigger off for that one insert.

## Notes

- Tests: batch-service `BatchServiceIT` 6 (real Postgres, stub inference: output/error files, 429 back-off re-runs the same line, cancel lets running lines finish, expiry fails the lines not run, invalid files → 400, another org → 404, delete); inference-service IT 14 (+2: batch priority 30, no buckets, one event id and start per line; 402 without credit, failed line not reported, malformed header 400); billing-service IT 7 (+1: batch at half price, trigger back on after the seed).
- CPU and GPU smoke pass with the batch section (3 lines → 2 answered + 1 failed at 400, usage `mode=batch` × 2, other org 404, delete, forged `batch-line` stripped by the gateway).
- Smoke found: the enterprise org of the admission section had no credit; on the slower GPU run its first chat was billed before the batch section, so it was flagged and got 402. It now gets a grant like the main org.
- `curl -F "file=@/tmp/…"` from Git Bash on Windows can't open the MSYS path (curl exit 26); the smoke sends the file on stdin (`file=@-;filename=…`), which works everywhere.
- **Billing bug found by the 10k-line bench (since phase 2):** `UsageReporter.report` emitted into a unicast sink from many threads; a concurrent `tryEmitNext` fails with `FAIL_NON_SERIALIZED` and the event was dropped (logged as "queue full or closed"). 2 of 10,000 batch lines lost their usage event; sync requests under concurrency could lose theirs too (= unbilled). Fixed with `synchronized` on `report` (and on the shutdown complete); regression IT: 8 threads × 250 reports, all delivered (1,725 of 2,000 without the fix).
- First bench run (before the fix): batch completed 10,000/10,000 in 923 s (10.8 lines/s) beside enterprise traffic (goodput 99.6%, TTFT p50 59 ms / p95 81 ms) and trial (43 answered, 366 refused); usage held 9,998 events, the 2 lost above. The script then died on `docker exec … touch /tmp/stop-bench` (Git Bash rewrote the path into a Windows one) and left its synthetic account, orgs and files in the local DB; it now runs those container-path calls with `MSYS_NO_PATHCONV=1` (only those: set globally, Windows curl can't open `-o /dev/null`, exit 23) and stops the workers from an EXIT trap.
- Second and third bench runs (after the fix): batch 10,000/10,000 in 993 s and 962 s, enterprise goodput 100% (TTFT p95 78–80 ms), usage exactly 10,000 events, but vLLM's own counter showed **no** line had run twice: the kill landed between lines, so the re-run path wasn't proven. The bench now kills only while a worker's transaction is open (`idle in transaction`) and counts vLLM's finished requests to show the re-runs.
- **Kill experiment** (2 slow lines, batch-service SIGKILLed mid-call): Postgres dropped the dead sessions at once (Docker resets the connections), both lines were claimed again and the batch completed ~7 s after the restart. But usage held the two **cancelled** first runs (estimated input, 0 output): their `ok` re-runs, which delivered 400-token answers, lost the event-id race. Fixed: a batch line reports usage only for a run that answered (`ok`); IT covers a cut-short line. Repeated: both lines billed once, `ok`, 400 tokens.
- vLLM does abort a cancelled non-streamed request at once (`num_requests_running` drops to 0), but aborted requests appear in none of its finish counters (`request_success_total{finished_reason="abort"}` stays 0). So the bench can't count re-runs from vLLM: inference-service now logs each batch line run cut short (ids only), and the bench counts those. A run with 256-token slow lines, killed while one was held, cut it short and all ten ran after the restart (usage: `ok`, 256 tokens each), but the vLLM-counter check reported 0 re-runs.
- **Exit check passed** (fifth run, `docker/batch-bench.sh`): batch 10,000/10,000 in 999 s (10.0 lines/s); enterprise 287/287, goodput 100%, TTFT p95 80 ms, TPOT p95 24 ms; trial 51 answered, 374 refused; batch-service SIGKILLed while a slow line was held: 1 line cut short and run again; usage exactly 10,000 events, 10,000 ids, all `ok`; no TTFT timeouts.
- **Second usage bug (since phase 2), found by the final CPU smoke:** `bufferTimeout(100, 1s)` → `concatMap(send)`: when a send was still running at the 1 s timer (a cold first POST after a restart), the flush had no demand → `OverflowException`, the pipeline terminated and every later report failed `FAIL_CANCELLED` until a restart (the smoke saw 1 of 3 usage rows). Fixed with `bufferTimeout(100, 1s, fairBackpressure = true)`; regression IT with a usage stub that takes 1.5 s per batch (1 of 4 delivered before, 4 of 4 after). CPU smoke green again; the only WARNs are Lettuce reconnects (Valkey stop step), the gateway's validator notices and billing's debit retries while usage-service restarted with the stack.
