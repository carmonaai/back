## G1 Rolling restart without failed requests (scorecard drill 6, gateway half)

What a restart looks like to a client, in order (`ShutdownDrain`, `GatewayDrainIT`):

| Time | What happens | What a client sees |
| --- | --- | --- |
| t0 (SIGTERM) | Boot publishes `REFUSING_TRAFFIC` first thing in `doClose()`; `ShutdownDrain` (phase `GRACEFUL_SHUTDOWN_PHASE + 1`, stops before the web server's graceful phase) marks the gateway draining | readiness on `:8081/actuator/health/readiness` answers 503 `OUT_OF_SERVICE`; a NEW request on `:8080` gets `503 {"error":{"type":"api_error","code":"server_draining"}}` with `retry-after: 1`, `retry-after-ms: 1000`, `connection: close`; requests already running are untouched |
| t0 + `carmona.gateway.drain-delay` (10 s) | Boot's graceful phase: Reactor Netty closes the listener, closes idle keep-alive connections, waits for running requests | new connections are refused at the socket; running streams keep flowing |
| until the last running request ends, at most `spring.lifecycle.timeout-per-shutdown-phase` (660 s) | the management server (`:8081`) closes only after that (phase `GRACEFUL_SHUTDOWN_PHASE - 512`), so the readiness probe answers 503 for the whole drain | a stream running at t0 ends whole; one still running at the timeout is cut |

Numbers and the reason for each:

- **drain-delay 10 s.** Longer than a balancer needs to see the probe change (compose probes every 5 s; Kubernetes removes the pod from EndpointSlices concurrently with SIGTERM, so it needs the same head start). During it the gateway refuses new requests instead of serving them: a stream that starts at t0 + 9 s would otherwise hold the drain for up to the full timeout.
- **drain timeout 660 s.** The longest request the gateway promises to finish: inference-service answers non-streamed requests within 600 s (`response-timeout`) and the inference route waits at most 660 s for response headers. inference-service has NO total cap on a stream (only 30 s to the first event, 30 s between events, `max_tokens`); a stream still running 660 s after the listener closed is cut.
- **grace period the runtime must grant: 720 s** (10 s + 660 s + margin). Docker Compose's `stop_grace_period` defaults to 10 s, then SIGKILL (docs.docker.com/reference/compose-file/services/#stop_grace_period): until the `har` chain sets `stop_grace_period: 720s` on the gateway, a compose restart still kills streams at 10 s. Kubernetes: `terminationGracePeriodSeconds: 720`.
- Both knobs are environment variables for the harness: `CARMONA_GATEWAY_DRAIN_DELAY`, `SPRING_LIFECYCLE_TIMEOUT_PER_SHUTDOWN_PHASE`.

Not covered by a test (no real SIGTERM): the packaged jar or container receiving SIGTERM from `docker stop`. `GatewayDrainIT` closes the application context, which is what Boot's shutdown hook does (`SpringApplicationShutdownHook.closeAndWait` calls `context.close()`). The Dockerfile's `ENTRYPOINT ["java", "-jar", ...]` is exec form, so the JVM is PID 1 and, having a SIGTERM handler, gets the signal directly (not tried in a container here). The scripted rolling restart (`har`) is the first end-to-end proof.

Sources: Spring Boot 4.1 reference, Graceful Shutdown and Kubernetes Probes (application lifecycle table); spring-boot 4.1.0 `ReactiveWebServerApplicationContext.doClose`, `WebServerApplicationContext` phase constants, `ChildManagementContextInitializer.getPhase`, `org.springframework.boot.reactor.netty.GracefulShutdown`; Reactor Netty 1.3.6 `ServerTransport.DisposableBind.disposeNow`; Kubernetes pod lifecycle, Termination of Pods.

The breaker still opens on what proves the hop sick: refused or hung connects, premature close, response timeout, a 504.
- The batch route is tested the same way as the inference route (`batchRouteHasItsOwnNamedBreakerAndFallback`, `batchRouteCountsOnly504`) and `everyConfiguredBreakerIsNamedByARoute` ties `ResilienceConfiguration.BREAKER_IDS` to the YAML: renaming a breaker in either place fails the build.
- The breaker is per replica (in memory); two gateways open independently.
- `UpstreamFailureHandler` answers the routes without a breaker (auth, accounts, organizations, billing, usage); since R1c it also writes the answers of the two breaker routes, which have no fallback any more.

### R1 review rounds 1 and 2 (history): the body cache could not be bounded

The first R1 moved the permit after the body and added `BodyIntakeFilter`, a counter of bodies being read (per organization and per replica), to bound what the body cache held. Round 2 of the review stopped it with one blocking and three major findings that share a root: both `/v1` routes declared `fallbackUri` since pass 1 (`f53a0eb`), so Spring Cloud Gateway cached every request body (`AdaptCachedBodyGlobalFilter` + `DataBufferUtils.join`), and the cost of that cache is per network read, not per byte. ## R1c Bodies stream: no `fallbackUri`, the answers come from the error path, per-organization upload share

Orchestrator decision, `work/pass-2/addenda/R1c.md`. What was done, in the order of its Decision section.

**1. `fallbackUri` removed from both routes** (inference, batch; `application.yaml`, and the Java copies of the routes in `StubUpstreamConfiguration` and `GatewayCircuitBreakerIT`). Nothing on a `/v1` route reads a body into memory any more.

**2. The answers moved to the error path.** Evidence, from the `spring-cloud-gateway-server-webflux` 5.0.3 jar (`javap -c`; there is no sources jar in the local repository):

| Class and method | What the bytecode does |
| --- | --- |
| `SpringCloudCircuitBreakerFilterFactory.apply(Config)` | `if (config.getFallbackUri() != null) enableBodyCaching(config.getRouteId())`: the only reason a route's body is cached. `AdaptCachedBodyGlobalFilter` (order `-2147482648` = `HIGHEST_PRECEDENCE + 1000`) keeps the set of such route ids (fed by `EnableBodyCachingEvent`) and calls `ServerWebExchangeUtils.cacheRequestBody` for them |
| the filter returned by `apply` (`$1.filter`) | `cb.run(chain.filter(exchange).doOnSuccess(status in statusCodes -> throw CircuitBreakerStatusCodeException), fallback).onErrorResume(t -> handleErrorWithoutFallback(t, config.isResumeWithoutError()))`. The fallback function is `if (config.getFallbackUri() == null) return Mono.error(t)`; only with a URI does it call `ServerWebExchangeUtils.reset`, rewrite the URL and `handle(dispatcherHandler, ...)` |
| `SpringCloudCircuitBreakerResilience4JFilterFactory.handleErrorWithoutFallback` | `java.util.concurrent.TimeoutException` becomes `ResponseStatusException(504, message, cause)`; `CallNotPermittedException` (breaker open) becomes `ServiceUnavailableException`, which is a plain checked `java.lang.Exception`, not a `ResponseStatusException`; `resumeWithoutError` gives an empty Mono (off here); anything else is `Mono.error(t)` unchanged |

| `ServerWebExchangeUtils.reset` | disposes `CLIENT_RESPONSE_CONN_ATTR` (the upstream connection) and removes the upstream response headers named in `CLIENT_RESPONSE_HEADER_NAMES` from the response, then `removeAlreadyRouted`. The forward did this; without it a counted upstream 504 would reach the client with the upstream's headers and keep the upstream connection |

So without a `fallbackUri` an open breaker, a timeout, a counted 504 and a refused or hung connect arrive at the `ErrorWebExceptionHandler` as `ServiceUnavailableException`, `ResponseStatusException` 504, `HttpStatusCodeException` 504 (`CircuitBreakerStatusCodeException`) and `ConnectException` / `ConnectTimeoutException` / `PrematureCloseException`. The exchange attribute `RouteBulkheadFilter.FALLBACK_CODE` is readable there: the attribute map is shared by every mutation of the exchange, and `UpstreamFailureHandler` already read it before this step (the existing ITs through the real handler, `connectsThatTimeOutOpenTheBreaker`, `batchRouteHasItsOwnNamedBreakerAndFallback`, `aConnectThatHangsAnswersTheSameRefusal`, are the oracle and pass unchanged). A rejected bulkhead is **not** an exception on these routes: `RouteBulkheadFilter` writes the 429 itself and never enters the breaker, and the starter's own bulkhead (the only source of `BulkheadFullException`) is switched off in `application.yaml` (`streamsOverTheBulkheadAreRefusedAndTheBreakerStaysClosed`: exactly 64 run, 36 get 429 `gateway_busy`, the breaker has 0 failures). The escape hatch of the decision (own byte-proportional cache) was not needed.

`UpstreamFailureHandler` (order -2, unchanged position) now answers, for a route that has a `fallback-code`, what `FallbackController` answered: a 504 anywhere in the cause chain (`ResponseStatusException` or `HttpStatusCodeException`) is 504 `api_error` `upstream_timeout`; everything else that failed behind the breaker is 503 `api_error` with the route's code (`inference_unavailable`, `batch_unavailable`) and `Retry-After: 30`. It calls `ServerWebExchangeUtils.reset` first. A committed response is left alone (a stream cut half way: the handler used to try to write a JSON refusal into an answer that was already going out). `FallbackController`, its test and the `/fallback` `permitAll` are deleted.

**Two consequences of streaming that the decision did not name, handled here:**

- *The breaker now sees the client's body.* The body is read inside the route's `CircuitBreaker` (the routing filter pulls it), where before the cache read it outside. Resilience4j records every error as a failure, so one tenant whose upload is too big, stalls or hangs up would have counted against the breaker shared by every tenant on the replica: 10 such uploads in a window of 20 open it for 30 s for everybody. `V1RequestFilter` now wraps every error of the inbound body in a `BodyFault`, `ResilienceConfiguration` ignores it (`ignoreException`: neither failure nor success), and `UpstreamFailureHandler` answers a `BodyFault` as it answered before (413 for the cap, 408 for the read timeout) and drops one whose client has gone. Test: `GatewayUpstreamFailureIT.uploadsThatStopComingNeverCountAgainstTheBreaker` (25 stalled uploads at once: 0 failed calls, breaker CLOSED), `ResilienceConfigurationTest`.
- *The 408 is written from the body's callback.* Netty's `ReadTimeoutHandler` closes the client's connection as soon as the exception returns; with the body streaming to the upstream the error reaches the error handler only after that, and the 408 was lost (`aBodyThatStopsComingIsCutAfterTheReadTimeout` failed). `V1RequestFilter.capped` writes the 408 itself on `ReadTimeoutException`, on the event loop, before the close. The 60 s `request-body.timeout` still closes the socket with no answer, as before. The upstream sees a request that stops half way (its own timeouts apply): inference-service must tolerate that.

**3. Permit and share (D3 under streaming).** `RouteBulkheadFilter` takes the permit when the call reaches the route (order `HIGHEST_PRECEDENCE + 2`), before a byte of the body is read, and holds it until the answer has been written (`GatewayUpstreamFailureIT.aStreamHoldsItsPermitUntilItEnds`: 64 streams running, the 65th gets 429). `BodyIntakeFilter` is renamed `UploadShareFilter` and keeps its counters, now keyed by **route id and organization**, with the share in the route metadata (`upload-share: 8` inference, `4` batch): at most that many bodies of one organization may be arriving at once on that route. The total counter is gone (the route's permits are the total), so the batch route cannot starve chat. Over the share: 429 `gateway_busy` before the body is read, and the call takes no permit (the share filter is at `+1`, the permit at `+2`). The share is given back when the body completes, fails or is cancelled, or when the chain ends if nothing read it, once.

**4. What bounds memory now (replaces every body-sized figure).** There is no body cache. A request body passes from Reactor Netty's server inbound to the client outbound buffer by buffer, with backpressure (`NettyOutbound.send` pulls from the inbound as the upstream connection drains), so the memory held per call does not depend on the size of its body or on how many network reads it arrives in: a few pooled Netty buffers per connection, and the same for the answer. Test: a 64 KB body written one byte per TCP segment (65536 reads) is forwarded whole to the upstream (the stub counts 65536 bytes) with the cache attribute never set (`aBodyThatArrivesOneByteAtATimeIsStreamedNotHeld`; the reviewer's reproduction with the cache held a gigabyte for 8 such connections). What bounds the number of calls in flight: on the two `/v1` routes the permits (64 inference, 16 batch, per replica), of which one organization can hold, while its body is still arriving, `upload-share` (8, 4); on the other routes (auth, accounts, organizations, billing, usage) the flood brake and the connection limits of the container, and their bodies are small JSON that streams too. Not measured: the real heap and direct-memory use of a loaded gateway (no harness in this module); the `har` chain's 50-stream run is where a container limit is chosen. There is no figure derived from body sizes to give it, so the earlier request to `har` (a `mem_limit` and a direct-memory ceiling sized on the old body-cache bound) is **withdrawn**: the gateway needs the ordinary requests and limits of hardening override 5, sized by that run. The edge does not have to buffer request bodies (nginx `proxy_request_buffering` would still help against slow uploads holding a permit, but nothing relies on it).

**5. Ceiling, stated.** Uploads are counted per organization, not per replica: a flood from many organizations (8 organizations with 8 stalled uploads each on the inference route) can still hold all of a route's permits for up to `request-body.timeout` (60 s; 10 s when the body stops entirely) and make the next calls answer 429 `gateway_busy` with `Retry-After`. That is shedding, not an outage of the other route or of calls already admitted. Upgrade if it matters: a rate per key at the edge, or nginx buffering request bodies so a slow upload never reaches the gateway.

**6. Guards that fail if a body cache comes back:** `GatewayUpstreamFailureIT.noV1RouteCachesItsBody` (a recorder `GlobalFilter` after `AdaptCachedBodyGlobalFilter` reads `CACHED_REQUEST_BODY_ATTR` on both production routes, one `GET` with a body and one `POST`; it fails if a `fallbackUri` or any filter that caches the body is added to either), `.aBodyThatArrivesOneByteAtATimeIsStreamedNotHeld`.

Alternatives rejected: keep `fallbackUri` and bound the cache (own one-buffer cache sized by `Content-Length`, the escape hatch): possible, but it keeps a copy of every body and the whole class of limits around it; a byte budget charged by `Content-Length` (counts bytes, not reads: the attack is reads); refuse small average reads (a heuristic on a hostile client); edge buffering only (not enforceable from this module).

Hand-offs. **G3** continues from `UpstreamFailureHandler` (the status-per-cause table and the malformed-request sweep) and must not reintroduce a forward. **G3b / G4 / G5 / X3** inherit "no body cache"; X3 (streaming `/v1/files` with a larger cap) needs only the timeout rule below and no memory ceiling. `work/tasks/P2-gw.md` (G3b done criterion) and the `har` brief carry the old body-cache memory statement (a figure for bodies held in memory): the orchestrator deletes it (those files are not in this workspace).

Request-body timeout and the files cap (hand-off to X3 / B3): `request-body.timeout` (60 s) is one global value for every route (Reactor Netty's server customizer cannot be set per route) and its reasoning ("a 4 MB body over a slow link is ~35 s") only holds while the cap is 4 MB. When X3/B3 raise the `/v1/files` cap to 100-200 MB, the timeout must be re-derived: minimum accepted upload speed = cap / timeout (100 MB in 60 s needs about 13 Mbit/s sustained; a slower customer would be cut with a closed socket, no 408, because the total timeout closes the channel). Raising it widens the idle-connection exposure of every route: each upload holds a route permit that long. Memory is not part of that calculation any more.

Other raw-path comparisons found and left alone, because they fail safe: `IdentityHeadersFilter.SESSION_PATHS` (an encoded `/auth/%72efresh` loses the refresh cookie, so the call is refused by auth-service), `AccessLogFilter` (the `/actuator/` skip decides whether a probe is logged; it applies to 8081 too, see G3). G3's malformed-request sweep should carry `%`-encoded spellings of every route.

Only the inbound body of a `/v1` request is renamed (to a `ResponseStatusException(408)` inside a `BodyFault`). Other routes' bodies (login JSON) still get Spring's empty 500 on a stalled upload: G3's sweep.

Logging: a client's stalled or dropped upload errors the request body that streams to the upstream, and Reactor Netty's `HttpClientConnect` logs that at WARN with a stack trace once per upload (seen in the first IT run: one WARN with a stack trace per stalled upload). `logging.level.reactor.netty.http.client.HttpClientConnect: ERROR` in `application.yaml` keeps a slow-upload flood from being a log flood; a real upstream failure is still answered, counted by the breaker and in the access log. ## G3 The error contract is complete and written down (decision 13 / C4)

Every response the gateway writes itself is `{"error":{"message","type","param","code"}}` (`param` always `null`; the gateway never blames a field) with `Content-Type: application/json`, an `x-request-id`, and **both** `retry-after` and `retry-after-ms` on every 429 and 503. Messages are fixed strings; the exception text, the request and the Netty decoder's message are never sent and never logged. `GatewayErrorContractIT` drives 49 causes through a socket as raw bytes (the sweep) and asserts all of that for each; `OpenAiErrorsTest` does the same for every writer and for 20 statuses.

Answers from an upstream (auth-service, inference-service, ...) pass through the gateway as they are, error bodies included: their shape is their service's contract (inference-service already answers in OpenAI's), not the gateway's.

### Decisions, and behaviour that changed

- **405 only from the firewall.** The gateway has no controller, so Spring's `MethodNotAllowedException` never occurs; the 405 the brief lists exists for methods the firewall does not allow, which the firewall refused with an empty 400 before. `GatewayApplication.METHODS` configures the firewall and fills `Allow`, so the two cannot drift. A method that is allowed but that no route accepts (`PATCH /v1/batches`: the batch route has `Method=GET,POST,DELETE`) is a 404: the router reports no route, not 'a route with another method', and a 404 does not tell a scanner which paths exist. (What OpenAI's own API answers for a wrong method was not checked here.) The inference route has no `Method` predicate: any method is forwarded to inference-service.
- **JWKS or key lookup down is 503, on both chains.** On the console chain it was a 401 (Spring maps a failure that is not a bad token to `AuthenticationServiceException`, and the entry point answered 401 for it): a client holding a valid token was told to log in again. It now gets the same 503 + `retry-after: 5` that `/v1` gives when the key lookup is down.
- **`/actuator/**` on 8080 is an ordinary 404** (shaped and numbered; not in the access log, like the probes on 8081). It was never served there.
- **No `Content-Type` check** (415): left to the upstream.
- **No body cap on console routes** (found, not changed): `V1RequestFilter` still caps only `/v1`; a console body is bounded by the 60 s `request-body.timeout` and the upstream's own limit. Cheap to add (`capped(exchange, 64 KB)` for `/auth` and `/accounts`); not asked for here.

## Deviations

Recorded for the orchestrator (rule, reason, alternatives); none changes a module rule or a hardening override.

1. **Hardening override 3, "a bulkhead per dependency".** The bulkhead still caps calls per dependency and now takes its permit before the body again (as before R1), so an upload holds a permit while it arrives. The conforming mitigation is the per-organization upload share (`UploadShareFilter`, `upload-share` on each route) plus Netty's read (10 s) and request (60 s) timeouts. Residual, stated in R1c item 5: many organizations can fill a route for up to 60 s. Alternatives not taken: permit after the body (needs a body cache, which is the defect R1c removes); an edge that buffers bodies.
2. **Config from `application.yaml`.** Boot 4.1 has no property for Reactor Netty's server `readTimeout` / `requestTimeout` (its `server.netty.*` keys do not include them), so two `carmona.gateway.request-body.*` properties feed a `NettyServerCustomizer` bean. Overridable from the environment like any property. `upload-share` is route metadata next to `max-concurrent`.
3. **The 408 for a stalled body is written from the body's callback** (`V1RequestFilter.capped`), not from the error handler, and is best effort (a client that has gone gets nothing); the 60 s total timeout never answers. Reason and alternatives in R1c above.
4. **A logger level raised**: `reactor.netty.http.client.HttpClientConnect` to ERROR (reason in R1c, "Logging").
5. **Scope.** `OriginFilter` is not in the four R1 findings; the same raw-path defect, three lines, so it is fixed with the shared-matcher approach (see the table). `IdentityHeadersFilter` and `AccessLogFilter` are left (fail safe). R1c also ignores the client's body faults in the breaker and makes `UpstreamFailureHandler` leave a committed response alone: both follow from streaming and are not in `R1c.md`.
6. **Breaker numbers stay in code** (`ResilienceConfiguration`), as before; the slow-call threshold is derived from the route timeouts by a test instead of a property.
7. **Plan section 9, "Error bodies are fixed OpenAI-style messages plus the request id" (G3).** The id travels in the `x-request-id` header, as the brief says, not as a field of the body: OpenAI's shape has no id field, and an SDK that parses the body strictly would have to be taught one. Nothing is missing for a customer: the header is on every response, and the access log has it.
8. **Spring Boot's error handling is no longer the gateway's (G3).** `GatewayErrorHandler` (order +2) answers every failure `UpstreamFailureHandler` leaves, ahead of Boot's `DefaultErrorWebExceptionHandler`, so `server.error.*` has no effect on port 8080. Alternative: configure Boot's `ErrorAttributes` to emit OpenAI's shape; rejected because it renders HTML by `Accept` header and cannot cover the Netty-level answers anyway.
9. **A Netty pipeline handler (`MalformedRequests`, G3).** Reactor Netty answers undecodable requests itself with an empty body and offers no hook, so a handler in front of `HttpTrafficHandler` rewrites its bare answers. It depends on Reactor Netty's pipeline name `HttpTrafficHandler` and on those answers being one `FullHttpResponse`; the 12 Netty-level rows of `GatewayErrorContractIT` fail if an upgrade changes either. Upgrade path: a decode-failure hook in Reactor Netty, if one appears.
10. **Reactor Netty's WARN for an undecodable request is rewritten, not silenced (G3).** Its default text quotes the decoder's message and the request line, which is the client's content in our log (plan section 9). `HttpServer.httpMessageLogFactory` keeps the exception class and `<filtered>` for the URI. Alternative: logger level ERROR for `HttpServerOperations`, which would also hide its other warnings and leave the refusal unlogged but for the access log line.
11. **Spring's `HttpWebHandlerAdapter` logger is OFF (G3 review).** Its ERROR line for an exchange that failed after the response was sent quotes the raw query string; `GatewayErrorHandler` logs `response already sent: <class> (request <id>)` in its place and passes on a fresh `Aborted` exception, not the original, because the original's suppressed Reactor checkpoint carries the same query string and Reactor Netty's `HttpServerOperations` logs suppressed exceptions at ERROR. Cost: any other unresolved error that reaches the adapter is silent from that logger (the handler's own line covers a committed response, and an unhandled exception is answered and logged by `GatewayErrorHandler` before it gets there). Alternative: a Logback filter that strips the query from that one message; more code for the same result.

**Gateway request-path hardening built 2026-10-08** (R1 and R1c, repair of G2; log: [pass-2-gw-progress.md](pass-2-gw-progress.md)): the `/v1` checks (4 MB cap, no Transfer-Encoding, no HTTP/1.0, no key in the URL) decide what is `/v1` with the matcher the API-key security chain is built on, so percent-encoded and `;`-parameter spellings of a path are judged exactly as the router and the chain judge them, and the 4 MB cap is also enforced on the bytes read, not only on `Content-Length`. New stores of personal data: none. The request body (prompts) is forwarded as it arrives and never held, written, logged or cached, so there is nothing to erase or export. ## G3b Flood brake limits as properties, sized for an enterprise key (D10 stopgap)

The prototype found the brake at 10 requests/s with a burst of 20 per caller (key id or account id): an enterprise key was refused far below what its tier admits. The sizes are now properties (`carmona.gateway.rate-limit.*`, defaults in `application.yaml`) and the default for an API key is derived from the biggest tier of inference-service. Per-key limits that follow the customer's plan are X1; this is the flat stopgap.

**The arithmetic** (sources: `api/inference-service/src/main/resources/application.yaml`, `carmona.inference.tiers`; `api/inference-service/src/main/resources/buckets.lua`; `Admission.keys/arguments`):

| Step | Value | Where it comes from |
| --- | --- | --- |
| Tier request limits, per organization and model | trial 20, standard 300, **enterprise 3000** requests-per-minute | `tiers:` in inference-service `application.yaml` ("prototype values, not commercial ones") |
| What a tier bucket does | holds `limit`, starts full, refills `limit/60000` per ms, admits while the level is at least 1, a refused request is not charged | `buckets.lua` |
| So the biggest tier admits | 3000 at once, then 3000/60 = **50 per second**; in any window of T seconds at most 3000 + 50 T requests of one organization on one model | the two rows above |
| One key can carry a whole organization | the key bucket must hold at least (burst 3000, 50 per second) for the brake never to refuse before the tier | the brake is per key id |
| The brake also counts what the tier never does | `GET /v1/models`, `/v1/files`, `/v1/batches` calls on the same key, and the tier is per model, so a key on a second model has a second bucket behind it | `RateLimitFilter` counts every call of the key |
| Shipped default | **burst 6000, 100 per second** (twice the tier) | headroom for the two rows above |
| Before | burst 20, 10 per second: 600 a minute sustained, a fifth of the enterprise tier's 3000, and 150 times short of its burst | the old constants |

Why twice and not exactly the tier: at exactly the tier's size the brake and the tier run dry at the same instant, and the brake sees more calls than the tier does, so it would win the race and refuse first. Twice is a round number that covers one more model at the full rate or as many non-chat calls as chat calls; a deployment that puts more than two models at the full enterprise rate behind one key, or that raises a tier, raises the key bucket too. `RateLimitPropertiesTest.theKeyBucketNeverRefusesBeforeTheBiggestTierDoes` reads the tiers from inference-service's own file and fails when the key bucket falls under the biggest tier (the invariant is "at least the tier", the factor 2 is the margin).

### What the brief and the plan assumed, and what the code does

| Claim | Finding |

**Recovery time was a defect and is fixed.** Lettuce reconnects with a delay that doubles from 1 ms to 30 s (Lettuce 7.5.2, `Delay.exponential()`: lower bound 0, upper bound 30 s, base 2, milliseconds; `DefaultClientResources.DEFAULT_RECONNECT_DELAY`). ### Found, not fixed (hand-offs)

1. **JWKS refetch is unthrottled and happens before the brake (security).** A token whose key id the replica does not know makes the gateway call auth-service `GET /auth/jwks` again, once per request (three tokens, three fetches in the IT). Those requests fail authentication in the security chain and never reach `RateLimitFilter`, so nothing limits them: an unauthenticated flood of made-up tokens becomes the same flood on auth-service, which also serves login. Smallest fixes, in order: rate-limit unauthenticated requests per client IP at the edge (nginx, platform.md); or give the decoder a `ReactiveJWKSource` that refetches at most once per N seconds (`NimbusReactiveJwtDecoder.withJwkSource`). Not done: outside G4's inventory and it edits `GatewayApplication.jwtDecoder`; wants a step of its own and a second reader.
2. **Two gateway replicas must not share the access-log volume.** `docker/compose.yaml` mounts the named volume `access-logs` at `/var/log/carmona`; with `--scale gateway=3` (the harness runs three) all replicas append to one `access.log` and each rolls it at midnight. Logback's own manual: "In prudent mode, `FileAppender` will safely write to the specified file, even in the presence of other `FileAppender` instances running in different JVMs" (logback.qos.ch/manual/appenders-console-file.html), and prudent mode with `TimeBasedRollingPolicy` allows neither compression nor the `file` property (appenders-rolling.html), which `logback-spring.xml` uses on both, so it is not a switch. A file name per instance would leave the files of replaced containers outside the 184-day cleanup. Request to `har` and the orchestrator: one log volume per replica (a short-lived scorecard run never reaches the midnight rollover, so nothing in the scorecard will show it), and for production the plan's "ship it to a store" decision. Not changed here.
3. **The gateway's Valkey calls have timeouts but no circuit breaker** (deviation 1 below): while Valkey is away every `/v1` call and every JWT call pays the 1 s command timeout (measured 1.04 s).
4. **Documents that disagree with the code** (for the orchestrator, Z1): `inference-plan.md` section 9 says suspension "auth-service deletes its `apikey:*` entries, 403 within the cache TTL": nothing deletes them (the bound is the 60 s TTL, which is what the phase 1 block says). The phase 1 block's "Gateway flood brake stays the in-memory per-replica limiter" is out of date (the brake has been in Valkey since the per-key token bucket). The brief's G4 premise (60 s key and credit cache) is wrong as the first table shows.
5. **Cold cache after a Valkey that lost its data**: every request of a key is a miss until the first lookup returns, and concurrent misses for one key each call auth-service (no coalescing). Bounded by the gateway's concurrency and auth's 2 s timeout; compose's Valkey persists (`appendfsync everysec`), so a restart keeps the entries. Not tested.

### Drafted architecture paragraph (voice of `inference-plan.md`; the orchestrator moves it)

**Gateway state across replicas inventoried 2026-10-08** (G4; log: [pass-2-gw-progress.md](pass-2-gw-progress.md)): the gateway keeps no cache of API keys or credit in its own memory. The key lookup cache (`apikey:{hash}`, TTL 60 s), billing's `no_credit:{organization}` flag and the flood-brake buckets (`rl:gw:*`, TTL 120 s) are Valkey's and shared by every replica, so a revoke and a credit change reach all replicas at once, a key's expiry is exact (compared on every request), and what the 60 s bounds is an organization's status and tier. A test with two gateway instances on one Valkey shows one brake bucket for the pair, one lookup for both, and the credit flag read per request. What each replica keeps to itself is the JWKS (for the life of the process, refetched on a token with an unknown key id, unthrottled), the route permits, upload shares and circuit breakers, and the local brake buckets that take over when Valkey fails. Valkey away is a documented degraded mode: `/v1` fails closed (503, `Retry-After: 5`, after the 1 s command timeout), console routes stay up and the brake fails open into one bucket per replica, so N replicas admit N times the rate; the gateways serve again within about 2 s of Valkey's return (0.4 s measured), because Lettuce's reconnect delay is capped at 2 s (its default grows to 30 s: 14 s and 24 s of further 503s after outages of 20 s and 40 s). Deviations, on purpose:
- No circuit breaker around the Valkey calls: each call pays the 1 s timeout while Valkey is away.
- The brake's fallback buckets forget a caller after 120 s idle, like Valkey's hash, so client IPs do not stay in memory.
- Open hazards handed on: unthrottled JWKS refetch before the brake (security); two replicas on one access-log volume.

New stores of personal data: none. State written by G4: nothing in Valkey or on disk (the tests read and write test keys in a container that is removed). Existing stores, stated for the inventory: `rl:gw:anonymous:{client ip}` holds a client IP for 120 s after the last request (Valkey `PEXPIRE`) and the fallback bucket for the same IP for 120 s idle (new, in memory); neither is exported (operational counters, not account data) and both leave on their own, so `DELETE /accounts/{id}` needs no action beyond the TTL; `rl:gw:account:{id}` holds an account or API-key id for the same 120 s. `apikey:{hash}` holds a key hash, key and organization ids, status, tier and expiry for 60 s (no personal data; erased by TTL or revoke). The access log (client IP, ids; 184 days, Marco Civil art. 15) is the one store here that outlives an erasure, by legal duty, as `inference-plan.md` section 9 already states.

Merge note (G3b + G4): `GatewayReplicasIT` sets `carmona.gateway.rate-limit.key.burst=30` and `.per-second=0.1` on both gateways, because the shipped key bucket (6000 at once, G3b) cannot be emptied within its 5000-call loop; the shared-bucket, fail-open and healing checks are unchanged. The G4 text above predates the G3b constants-to-properties change; where it names `ANONYMOUS_*` or an `account` bucket for `/v1`, read the properties and the `key` bucket.

Drafted architecture paragraph for G3 (voice of `inference-plan.md`; the orchestrator moves it):

**Gateway error contract built 2026-10-08** (G3; log and the status-per-cause table: [pass-2-gw-progress.md](pass-2-gw-progress.md)): every response the gateway writes itself, whoever produces it, is OpenAI's `{"error":{"message","type","param","code"}}` (`param` null) with `Content-Type: application/json`, an `x-request-id` and, on every 429 and 503, both `retry-after` and `retry-after-ms`. That covers the filters and security chains, Spring's own failures (no route is a 404, a method the firewall does not allow is a 405 with `Allow`, a path it refuses is a 400, an unexpected exception is a 500 `internal_error`), an upstream whose name does not resolve (503), and what Reactor Netty answers before WebFlux has an exchange (undecodable request, line or headers too long, bad percent escape: 400, 414, 431), which a handler in the Netty pipeline gives a body, a request id and an access-log line. Answers from an upstream pass through as they are. The causes are not enumerable by hand, so `GatewayErrorContractIT` sends 49 of them as raw bytes (the malformed-request sweep) and checks the shape, the id, the retry pair, that nothing of the request is echoed, and that no log line outside the access log contains it (Reactor Netty's own WARN for an undecodable request quoted the client; it now logs the exception class; Spring's `HttpWebHandlerAdapter` ERROR for an exchange that failed after its response was sent quoted the raw query string; that logger is off, `GatewayErrorHandler` logs the exception class and the request id, and it passes on a fresh message-less exception because the original's suppressed Reactor checkpoint would otherwise reach Reactor Netty's own ERROR line). 499 exists only in the access log: a client that hung up before a status was chosen. Deviations, on purpose:
- The request id is a header, not a field of the body (OpenAI's shape has none).
- Reactor Netty has no hook for its own answers, so `MalformedRequests` rewrites any bare 4xx/5xx `FullHttpResponse` without an `x-request-id` in front of `HttpTrafficHandler`; it depends on that pipeline name.
- A key lookup or JWKS that is down is a 503 on the console routes too (it was a 401 there), and `/actuator/**` on port 8080, which nothing serves, is an ordinary shaped 404 (numbered, not recorded: the access log still skips `/actuator/`, which also keeps the management port's probes out of it).
- A method a route declines is a 404 (the router has no route to report); the 405 exists only for methods the firewall refuses.
- Nginx's own error pages, when the edge exists, are not covered: it needs `error_page` with the same JSON.

New stores of personal data: none. The error bodies are fixed strings; the request, the decoder's message and the exception text reach neither a client nor a log line of ours (Spring's `HttpWebHandlerAdapter` logger, which printed the raw query of a request that failed after its response was sent, is off; the access log records the request id, address, status and, for requests WebFlux saw, method and path, as before).

A fourth review found the answer missing for an exchange that fails BEFORE the response is committed with an exception that only reads like a disconnect (`DisconnectedClientHelper` matches the message "broken pipe" / "connection reset by peer", which is what an upstream RST produces on Linux): `GatewayErrorHandler` skipped it as "client gone", and the Spring adapter then wrote an empty-body 500 (and a console route with a plain `SocketException` got a 500 `internal_error` without `retry-after`). Fixed in two places: `GatewayErrorHandler` now skips only a committed response and answers every uncommitted exchange (the 500 `internal_error` for a disconnect-looking exception, class logged at DEBUG, as `HttpWebHandlerAdapter` answers first and asks about the client after), and `UpstreamFailureHandler.unreachable` treats any `IOException` (which already covers `ConnectException`, `ConnectTimeoutException`, `PrematureCloseException`, `UnknownHostException`) or `TimeoutException` as the 503 `service_unavailable`. The committed branch and the fresh `Aborted` are unchanged. Tests: two sweep rows with an upstream call that fails with `IOException("Connection reset by peer")` (console 503 `service_unavailable`, /v1 503 `inference_unavailable`), `UpstreamFailureHandlerTest` for `IOException` / `SocketException` / a nested one, and `GatewayErrorHandlerTest` now expects the JSON answer for an uncommitted "Broken pipe" and the quiet `Aborted` for a committed one.

## G5 Spread upstream calls across replicas (D9)

The prototype's finding: with `--scale inference=3` behind the shipped gateway all traffic went to ONE replica (deltas 12/0/0; 0/12/0 after a gateway restart) although Docker DNS returned three addresses. The mechanism, read from Reactor Netty 1.3.6 (`TransportConnector`, tag v1.3.6; `javap` of the 1.3.6 jar for the selector API) and then reproduced:

| Cause | Evidence |
| --- | --- |
| Every new connection dials the FIRST address of the resolved list and tries the next one only after a connect failure (`doResolveAndConnect`, `selectedAddresses`, `doConnect(... index)` then `RetryConnectException`) | source; mutation M0 below: with the fix removed the same IT sends `[300, 0, 0]` |
| The resolver caches the answer for the record's TTL; Docker's embedded DNS answers 600 s and shuffles per query, so the cache freezes ONE shuffle for ten minutes | the 600 s and the shuffle: researcher's reading of moby `resolver.go` on master, **not measured here** (the IT's fake DNS answers with TTL 600 like Docker). That the TTL cap decides the outcome: mutation M3 (cap removed: a replica that left keeps its traffic, one that joined gets none) |
| The pool is keyed by the unresolved `host:port`, not by address, and a warm pool never resolves again | mutation M1 (pool back, rotation on): sequential requests `[0, 300, 0]` |

### What was chosen, and what was not

`ReplicaSpread` is an `HttpClientCustomizer`, so it applies to every route's client; `GatewayApplication.auth` applies it to the WebClient that calls auth-service, the gateway's only other outbound HTTP call (that client keeps a small pool, see the review fix below). It does three things: (1) `httpclient.pool.type: DISABLED` in `application.yaml`, one connection per request, closed after the answer; (2) the cached DNS answer is capped at `carmona.gateway.upstream.dns-cache-ttl` (5 s); (3) `resolvedAddressesSelector` starts each new connection one address further along the list (strict rotation from one counter) and keeps the rest of the list in order behind it, so a refused or timed-out connect falls over to the next replica within the same request.

| Option | Why not |
| --- | --- |
| `roundRobinSelection(true)` only | a random rotation, and the pool still pins sequential traffic; on 300 requests a random pick leaves +/-25 % of equal with a probability of about 0.5 % per run (my normal-approximation estimate): a flaky acceptance test |
| keep the pool, bounded `max-life-time` / `max-idle-time` | spreads per connection over time, not per request: sequential or low-concurrency traffic stays on one replica for the connection's life; and a pooled socket to a replica that restarted fails on reuse (and the breaker counts it) |
| Spring Cloud LoadBalancer with a DNS-backed instance supplier | the library has no DNS supplier (custom code), a new dependency, `lb://` on every route, and no free fail-over to the next address |
| balance outside the JVM (nginx between gateway and inference, Kubernetes) | the brief wants no new component; the harness may still put one there, and this change is harmless then |

Cost, stated as a `ponytail:` ceiling in `ReplicaSpread`: a TCP connection per request. The gateway closes first, so it holds the TIME_WAIT entries; Linux's default ephemeral range (32768-60999, 28 232 ports) is per destination address and port, so about 470 requests per second per replica address before connects start to fail. The inference route is far below that (64 calls at a time per gateway, each lasting seconds). Not measured on a Linux container here. Upgrade if it matters: keep the pool and set `max-life-time`, or Spring Cloud LoadBalancer. Kubernetes: a ClusterIP is one virtual address and kube-proxy balances per connection, so a pooled keep-alive client pins a pod exactly like Docker DNS did; with no pool every request is a new connection and is balanced per request. A headless service (an A record per pod) behaves like Docker DNS here (CoreDNS answers a TTL of 5 s, the same as the cap).

### What the gateway does when the fleet changes (`GatewayReplicaSpreadIT`)

The IT runs the production gateway (its `application.yaml`, `ReplicaSpread`, the real Netty resolver) against a small DNS server of its own (UDP, A records with TTL 600 like Docker) and three stub upstreams on 127.0.0.1-3, the same port. `carmona.gateway.upstream.dns-server` (unset in production: the system resolver) and `carmona.auth.url` are the two seams it needs. Each test has its own name, so the resolver cache of one test never leaks into another (the class runs in random order).

| steady state, sequential | exactly even | `sequentialRequestsAreSpreadEvenlyAcrossTheReplicas`: 300 requests, `[100, 100, 100]`. The plan's bound is 75..125 each (+/-25 %) and is what the test asserts |

A replica that still accepts TCP but answers slowly or not at all stays in rotation: a third of the requests wait for it until the route's `response-timeout`, and what opens is the route's breaker (shared by all replicas of the route), for everybody. To my knowledge (not tested here) Docker Compose keeps a container with a failing healthcheck in its DNS answer; only an orchestrator that removes unready replicas from DNS (Kubernetes endpoints) makes readiness count. ### Every Feign client between services, and "can it pin one replica?"

Five `@FeignClient` interfaces, all with a fixed `url="${carmona.<svc>.url:http://<svc>:8080}"` (grep over `api/*/src/main`):

| Client (library) | Called by (service) |
| --- | --- |
| `AccountController` | auth-service |
| `AuthController` | account-service |
| `BillingController` | usage-service |
| `OrganizationController` | account-service, auth-service (`ApiKeyService`), batch-service (`BatchFinisher`), billing-service, usage-service |
| `UsageController` | billing-service |

**All five can pin**, by the same mechanism but weaker. What I checked: no `api/*/pom.xml` has feign-hc5, okhttp, httpclient5 or a load balancer, and every `url=` is set. The rest is reading, not measurement (researcher 2, JDK 25 and Spring Cloud OpenFeign 5.0.3): a fixed `url=` bypasses Spring Cloud LoadBalancer even when it is on the classpath, and with no HTTP client library Feign uses `HttpURLConnection`, which takes the first address of `InetAddress.getAllByName`, cached by the JVM for 30 s by default (`networkaddress.cache.ttl` is not set anywhere in the tree). So a caller JVM sends its new connections to one replica per 30 s window, and keep-alive sockets (JDK idle limit 5 s, then the server's own limits) keep a steady caller on its replica longer. Callers decide independently, so the fleet average evens out where there are many callers, and Docker's per-query shuffle picks another replica in the next window. It is not the ten-minute freeze the gateway had.

What I did about them: **nothing in code, on purpose.** They live in modules this step does not own (edits there are lost), nothing in the stack is scaled behind a Feign call today (`docker/compose.yaml` has no replicas; the scaled hop of this pass is gateway to inference, and inference-service is not called by Feign), and the fixes are not small: (a) Spring Cloud LoadBalancer with a DNS-backed supplier and no `url=` in five libraries (new dependency, custom supplier), (b) a custom `feign.Client` that rotates addresses (the `ReplicaSpread` approach, per service), (c) balance outside the JVM (a Kubernetes Service, nginx). Proposed decision for the owner: when a service behind these is scaled for load, do (c) in Kubernetes and (b) in compose.

Other HTTP callers that pin the same way and belong to other chains (listed so their owners see them): `BatchWorker` in batch-service calls `http://inference:8080` with `java.net.http.HttpClient` (the JVM DNS cache plus its own connection pool); inference-service's `Engine` and `Reconciler` use pooled Reactor Netty WebClients to `${ENGINE_URL}` (4 s idle limit; a name with several engine replicas would pin like the gateway did, and `docker/compose.yaml` has `ENGINE_URL: http://llama:8080`) and to `http://usage:8080`. nginx in front of the gateway (`platform.md`: `server gateway:8080;`) resolves the name when it loads its configuration and then uses all addresses round-robin (nginx `ngx_http_upstream_module`, the `server` directive; not tested here): it balances but does not follow a scale change until reloaded or given a `resolver`.

### Review fix: the auth client keeps a pool (adversarial finding, major)

The first G5 commit gave the auth WebClient `HttpClient.newConnection()`. A key that is not in Valkey is looked up at auth-service; the CRC in the key format is public, so anyone can mint endless valid-looking unknown keys, and authentication runs before the rate limiter. With a connection per lookup that is an unauthenticated way to fill the gateway's TIME_WAIT sockets towards `auth:8080`, which login, register and refresh share (about 470 lookups per second per address on a default Linux range; the Linux figures are the implementer's, not measured). Fix: `GatewayApplication.auth` uses a pool of at most `AUTH_CONNECTIONS` (32) connections with `maxLifeTime` 5 s and `pendingAcquireTimeout` 2 s: at most about 6 new connections per second whatever the lookup rate, and a lookup that finds the pool busy for 2 s fails (503, fail closed) instead of queueing. The price: the auth client spreads per connection (the rotation still deals each new connection to the next replica), not per lookup, and a connection lives 5 s. `GatewayReplicaSpreadIT.aFloodOfUnknownKeysDoesNotOpenAConnectionPerLookup`: 700 unknown keys from 128 clients used 32 connections (bound 32), login answered during and after the flood; after 6 s idle, 300 more replaced every connection (64 in all, bound 64). `aBusyAuthPoolFailsClosedWith503InsteadOfQueueing`: stubs hold lookups 1.5 s, 96 lookups at once (32 + the 64 that Reactor Netty's default queue holds): 64 served, 32 refused 503 `service_unavailable` with `Retry-After` at 2 s, 32 connections, login 200. Mutations (review round): `pendingAcquireTimeout` 60 s fails the busy-pool test (4.5 s, all served); `maxConnections(100000)` fails both; `maxLifeTime` 1 h fails the flood test (no connection replaced: 32 in all); `maxLifeTime` 50 ms failed it before. A first version of the busy-pool test did not catch the 60 s timeout: the 503s there came from the queue limit (`pendingAcquireMaxCount`, default 2 x the pool), not the timeout; the test now stays inside the queue. Mutation: `HttpClient.newConnection()` back: 700 connections, that test fails (and 401 expected but 200 in the other lookup test when its keys collided with seeded ones, a test bug fixed by a distinct key prefix). Other routes, including login and register, still open a connection per request; they are reachable without credentials but the rate limiter keys them by client IP, and an unknown-key flood no longer reaches them. Left open (ponytail comment in `GatewayApplication.auth`): a per-IP brake on lookups that miss the cache, if a flood must not even cost the pool; while the pool is saturated, new keys get 503 until it clears, and cached keys and JWTs are unaffected.

### Review fixes, round 3 (adversarial and correctness findings, three majors)

1. **The JWKS fetch has its own pool** (`GatewayApplication.jwtDecoder`, `JWKS_CONNECTIONS` = 2, same 5 s life and 2 s acquire timeout): a bulkhead per dependency use. Before, a flood of unknown API keys (public CRC, authentication before the rate limiter) kept the 32-connection lookup pool and its queue full, and a JWKS refresh (5-minute cache, or an unknown `kid`) was refused, so console JWTs stopped validating. Test: `GatewayReplicaSpreadIT.aFullKeyLookupPoolDoesNotStopTheJwksFetch` holds the lookup pool full (32 connections busy, 64 queued) and decodes a signed token that needs the first JWKS fetch of the context; it fails when the decoder uses the `auth` client again (the queue is full, the fetch is refused).
2. **`aBusyAuthPoolFailsClosedWith503InsteadOfQueueing` no longer bounds the elapsed time** (3.8 s against clean runs of 2.6 to 3.7 s, mutation 4.5 s: false reds on a loaded host). The 60 s `pendingAcquireTimeout` mutation is caught by the count of 503s (`hasSizeBetween(32, 40)`: zero refused).
3. **The flood test asserts `isSubsetOf(401, 503)`** instead of `containsOnly`, which also demanded at least one 503; those need all 128 clients to arrive while the stubs hold the pool, and the busy-pool test owns them.

### Deviations (G5)

Recorded for the orchestrator (rule, reason, alternatives).

1. **"Services are stateless, so replicas scale horizontally" (SKILL.md, Shape) does not hold for the Feign hops as built**: a caller pins a replica for the JVM's DNS-cache window (30 s) and for as long as its keep-alive sockets live, because every `@FeignClient` has a fixed `url=`. Not changed here (not the owned module; nothing scaled behind them today). Alternatives and the proposed owner decision: see the Feign section.
2. **The default of pooled connections is given up on purpose** for the gateway's route calls (one TCP connection per request; the auth client keeps a small short-lived pool, review fix above); hardening override 3 (timeouts, breaker, bulkhead per dependency) is untouched. Reason and ceiling above. Alternative: a pool with `max-life-time`, which does not balance per request.
3. **Two config seams for the test**: `carmona.gateway.upstream.dns-server` (empty in production) and `carmona.auth.url` (default `http://auth:8080`, unchanged). Config still comes from `application.yaml`. Both could go if the IT had another way to inject a resolver and a base URL. `dns-server` takes an IPv4 `host:port` only.
4. **No per-replica health checking** (above); the breaker is per route. Outlier ejection per replica would be a new component (a balancer in the data path), not a setting.

### Drafted architecture paragraph (voice of `inference-plan.md`; the orchestrator moves it)

**Gateway upstream balancing built 2026-10-08** (G5, D9; log: [pass-2-gw-progress.md](pass-2-gw-progress.md)): a name with several replicas behind it (compose `--scale`, a headless Kubernetes service) is now balanced per request by the gateway itself. Reactor Netty dials the first address of the resolved list for every connection, caches the answer for the record's TTL (Docker says 600 s) and keys its pool by name, so the shipped gateway sent every request to one inference replica. The gateway's HTTP client now opens a connection per request (`httpclient.pool.type: DISABLED`), trusts a DNS answer for at most 5 s (`carmona.gateway.upstream.dns-cache-ttl`), and starts each connection one address further along the list, keeping the rest in order so a dead replica that is still in the DNS costs no request. The gateway's calls to auth-service are balanced per connection: a pool of 32 connections that live 5 s, because a connection per lookup would let a flood of unknown API keys use up the ephemeral ports towards auth. Proven on 300 requests across three stub replicas behind one name (exactly 100 each; the bound is +/-25 %); a replica that leaves the DNS gets nothing after 5 s (bound 10 s) and one that joins gets traffic within 5 s. Deviations, on purpose:
- One TCP connection per request: a ceiling of about 470 requests per second per replica address on a default Linux ephemeral range; the inference route is far below it. Upgrade: a pool with `max-life-time`, or Spring Cloud LoadBalancer.
- No health checking per replica: a replica that accepts connections but answers slowly stays in rotation, and the route's shared breaker is what opens. Only an orchestrator that takes unready replicas out of DNS (Kubernetes) makes readiness count; Compose does not.
- The five Feign clients between services keep their fixed `url=` values and can pin a replica for the JVM DNS-cache window (30 s) and their keep-alive sockets; nothing behind them is scaled today. Fix when one is: Kubernetes Service balancing, or the same rotation in a custom `feign.Client`.

New stores of personal data: none. DNS answers (addresses of our own services) are cached in memory for at most 5 s; nothing personal is read, logged, cached or sent anywhere new.
