## Design decisions (keep consistent when resuming)

- **Output reservation** (`Admission`): admitted while every bucket holds at least 1, as before; the output bucket is now charged `max_tokens` (the request's, or the model's cap when absent) at admission, and `real output − max_tokens` when the request ends (complete, error or cancel: `settle` runs in the engine call's `doFinally`). A request refused by a cap after its buckets were charged gets its `max_tokens` back at once (it generated nothing); its request and input estimate still count, as before. `Permit.charged` says whether the buckets took the reservation, so a request admitted while Valkey was down is settled with its real counts and never refunded. Overshoot is now one request's `max_tokens` per burst instead of in-flight × `max_tokens`. With the prototype limits, max in flight × 1024 is below every tier's output budget (trial 2 × 1024 < 10,000 a minute), so the reservations of running requests alone can't empty a bucket.
- **Usage stream** (`UsageReporter`): `XADD usage:events * event <json>` as each request ends (retried with backoff for ~25 s, then an ERROR line with ids and counts). A relay per instance, consumer group `usage-relay`, consumer = `HOSTNAME`: every second, `usage-next.lua` claims entries some relay read but didn't confirm within `usage-claim-after` (60 s; 10 s in compose), else reads new ones (100 at most), and creates the group on first use or after Valkey lost it. One POST per batch; 202 → `XDEL` then `XACK` (an entry acknowledged but not deleted would stay forever; a deleted one left pending is dropped by the next claim); 400 → the batch is resent one event at a time and only the rejected event is dropped (ERROR line); anything else, a wrong URL's 404 included → the entries stay pending and are claimed again. Passes repeat while batches come back full. Delivery is at least once; usage-service's key `(event_id, started_at)` makes it exactly once in storage.
- **Valkey persistence**: `--appendonly yes --appendfsync everysec`, volume `valkey-data`. A crash of Valkey itself loses about a second of writes. The other keys (API-key cache, `no_credit` flags, rate buckets) are now kept across restarts too; all of them expire or are re-synced on their own.
- **Reconciliation** (`Reconciler`, plan §8): every `reconcile-every` (1 h), per model, the increase of the engine's counters since the last reading is compared with usage-service's totals of every event received meanwhile, whatever its status (`GET /usage/totals?from&to`, by `received_at`). llama.cpp: input = `llamacpp:prompt_tokens_total` + `llamacpp:prompt_tokens_cached_total` (its prompt counter excludes cache hits), output = `llamacpp:tokens_predicted_total`; its `/metrics` needs the engine key. vLLM: input = `vllm:prompt_tokens_total`, output = `vllm:generation_tokens_total`. Agree when the gap is within max(0.5%, (slots + queue) × context window): requests in flight across a window's edges are counted on one side only. INFO when they agree, WARN when not; the first reading after a start or an engine restart is only a reading.

## Notes

- Research 2026-10-04: OpenAI counts the larger of `max_tokens` and a character-count estimate toward its token limit and documents no give-back; Anthropic's live rate-limit page says `max_tokens` no longer counts toward OTPM (output is counted as generated), while its early-2026 page estimated OTPM from `max_tokens` and adjusted it at the end. Ours is the conservative variant of the latter.
- vLLM v0.30.0 counters (source at the tag): `vllm:prompt_tokens_total` adds a request's whole prompt (cache hits included) once, at the step that emits its first token, never again after a preemption; it equals `usage.prompt_tokens` for n = 1. `vllm:generation_tokens_total` adds every token generated for a live request. A client gone before the first token is counted nowhere by vLLM (our event bills the input estimate); after it, the prompt and everything generated until the abort are counted (we bill input plus the output seen). `/metrics` isn't behind `--api-key`: engines stay on the internal network. `--disable-log-stats` would zero the counters.
- llama.cpp counters, measured on the running stack: a plain chat (22 prompt, 3 cached, 12 completion) moved `prompt_tokens_total` +19, `prompt_tokens_cached_total` +3, `tokens_predicted_total` +12; the same chat again +1 / +21 / +12; a client that hung up after 46 content chunks was still counted, 47 generated tokens (its usage event is an estimate on this engine).
- A Lettuce command that times out may still run on the server, since it was already sent: an `XADD` retried after a timeout can land twice. The duplicate stream entries are harmless (usage-service keeps one per event id); the Valkey-pause IT goes through this path.
- `XREADGROUP` (without `BLOCK`) and `XAUTOCLAIM` run inside a Lua script on Valkey 9.
- Tests: inference-service IT 23 (+6) and `ReconcilerTest` 2; usage-service IT 5 (+1). CPU and GPU smoke green; in the crash check the restarted instance delivered the three claimed events 3.6 s after its container started (compose's 10 s claim works through `CARMONA_INFERENCE_USAGECLAIMAFTER`: a record property drops its dashes in an env name).
- Reconciliation on vLLM under `bench.sh` load, every 30 s (a local override): each window's engine and usage counts differ by the requests in flight at its edges; summed over the run they match exactly, 1,672 input and 9,728 output tokens on both sides.
