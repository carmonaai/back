**Revenue leaks closed 2026-10-04** (log: [revenue-leaks-progress.md](revenue-leaks-progress.md); gaps 1 and 2 of the handoff's review): the output bucket takes each request's `max_tokens` at admission and gets back what wasn't generated when the request ends, so a burst passes the per-minute limit by one request's `max_tokens` at most (was: in flight × `max_tokens`). Usage events are written to a Valkey stream before anything else, and a relay delivers them to usage-service and deletes them once stored; a killed inference-service loses none (Valkey keeps an append-only file). Every hour each engine's token counters are compared with the usage stored (§8). Deviations, on purpose:
- The durable buffer is a Valkey stream with a consumer group, not Kafka: one consumer (usage-service, over HTTP) and Valkey already on the path. Kafka when an event gets a second consumer (§12).
- The relay lives in inference-service and keeps usage-service's HTTP contract; usage-service doesn't read the stream itself.
- A crash between an answer's last byte and its `XADD` (about a millisecond) still loses that event; billing before answering would add latency to every request.
- The reconciliation logs (INFO, WARN past the tolerance) instead of alerting: there is no alerting stack yet. Its tolerance is max(0.5%, (slots + queue) × context window), because requests in flight across an hour's edges count on one side only; each replica reconciles every model.
- Valkey's other keys (API-key cache, credit flags, rate buckets) now survive restarts too; each expires or is re-synced on its own.

**Flex processing built 2026-10-04** (gap 3 of the handoff; OpenAI's `service_tier: "flex"`): a live `/v1/chat/completions` request with `service_tier: "flex"` runs in the batch lane: vLLM priority 30, only while the model is at most half busy (the batch lines' share, whatever the organization's tier), at batch prices. With no spare capacity it gets 429 `resource_unavailable` at once and is not billed, so clients retry with backoff or without the tier, as OpenAI's guide says. `auto` and `default` are the standard lane; any other tier is 400 `unsupported_service_tier`. Deviations, on purpose:
- Flex usage is recorded as mode `batch`, the half-price lane billing already prices: no usage or billing migration. ponytail: a `flex` mode of its own (CHECK constraints, prices, `UsageService.MODES`) when flex needs a price or a report apart from the Batch API.
- The organization's rate buckets and in-flight cap still apply (batch lines skip them): flex is cheaper, not a way around the limits.
- Responses don't carry `service_tier`: a flex request is either served as flex or refused, never moved to another lane.

**Bounded wait, intra-tier fairness and capacity metrics built 2026-10-06** (gaps 6 and 4 of the handoff): a paying tier (`standard`, `enterprise`) that meets an in-flight cap now waits up to `admission-wait` (1.5 s default, well under the 30 s TTFT timeout) for a slot and is refused only when none frees; trial, flex and batch lines keep the instant 429, they are the shed-first traffic. The wait holds no thread (`Mono.delay` + re-check) and is cancelled with the request, so a client that hangs up leaves nothing behind; the failure is byte-for-byte the 429 of an immediate refusal, and the rate buckets are still charged once per request and given back once on the final refusal, however many attempts the wait made. Within one model the *waiting* requests are ordered by their organization's virtual token counter (VTC, OSDI '24): `estimatedInputTokens + max_tokens` charged at admission and settled to the real counts as the request ends, lowest counter goes first, so one organization cannot hold every slot of its tier while another waits. Capacity and latency are now visible on the management port (Micrometer, the names a contract with the dashboards): `carmonai_inference_ttft_seconds`, `..._itl_seconds`, `..._queue_wait_seconds` and `..._request_seconds`, each with the explicit histogram buckets of the brief's table (`le` in seconds), tagged `model` and `tier`; `carmonai_inference_requests_total{model,tier,outcome,code}`, `carmonai_inference_tokens_total{model,mode,kind}`, `carmonai_inference_inflight{model}`, `carmonai_inference_capacity{model,tier}`, `carmonai_inference_reconcile_mismatch{model}` (1 = the engine's counters and the usage stored disagree: usage, and revenue with it, is going missing; 0 = they agree, absent until a model has two readings to compare), and the engine's own `carmonai_engine_requests_running|requests_waiting|cache_usage{model}` read in the reconciler's existing scrape. `GET /actuator/reconcile` runs the usage check on demand, on the management port only. Deviations, on purpose:
- VTC orders waiters and nothing else: no second cap, the tier share and the per-organization `maxInFlight` are untouched, and a waiter still passes through `acquire()`. A waiter that is refused by its own organization's cap drops out of the ordering for that turn rather than blocking a slot it cannot use.
- The counter is per model and organization in memory (gap 5 still open: one replica's view only) and entries with nothing in flight and nobody waiting are dropped after 10 idle minutes, so an organization back after that starts from zero.
- The wait is a 100 ms poll, not a wake-up per release: a slot that frees just after a look waits one poll. A permit-released sink is the upgrade if that ever shows in the queue-wait p95.
- `carmonai_engine_*` gauges refresh at `reconcileEvery` (1 h by default), which is a slow trend, not a live gauge: an engine metric the exposition does not carry stays *absent* rather than reading as a false 0. Per-second scraping into memory is still the >1-replica work of §7, with a timer of its own.
- `carmonai_inference_request_seconds` and the request counter cover requests that reached admission (a valid model and tier): a body that fails to parse, or a model that does not exist, has no `model` tag to be counted under. Refusals count once, with their code; requests that ended have `code="none"`.
- The timers publish explicit `le` buckets, not client-side `quantile` series: Micrometer's Prometheus registry drops `publishPercentiles` as soon as a timer carries histogram boundaries (checked against a real scrape: the boundaries won and the quantiles vanished), and client-side quantiles do not aggregate across replicas. p50/p95/p99 come from `histogram_quantile()` over the buckets, which is what an alert rule computes over anyway.
- A request's bucket settlement is written before its usage event and its metrics: it is the correction the next request from that organization sees, and it left a race (a second request arriving while the first request's refund was still in flight) when the event and the metrics went first.

**API key lifecycle built 2026-10-05**: a key can expire and can be rotated. `api_key.expires_at` is nullable (`V2026.10.05.001__api_key_expiry.sql`) and null means "never expires", so every key issued before the migration keeps working; `POST /organizations/{org}/api-keys` takes an optional `expiresAt` (ISO-8601 in the body, no `@DateTimeFormat`) and an expiry that has already passed is a 400; `ApiKeyOut` and the internal lookup answer carry `expiresAt`; the lookup the gateway uses asks for "not revoked **and** (no expiry **or** expiry in the future)" in SQL against the database clock, so a skewed service clock can't expire a key early. `POST /organizations/{org}/api-keys/{id}/rotate` issues the new key and revokes the old one in one transaction and returns the new secret once, keeping the old key's expiry. Deviations, on purpose:
- An expired key and a revoked one are the same thing on the wire: both 404 on the internal lookup, so the gateway answers 401 `invalid_api_key` for either. There is no `key_expired` code to leak which of the two it was.
- Rotating keeps the old key's absolute expiry (a 90-day key does not get a fresh 90 days, and the rotation of a key that has days left dies with it). Rotating a key that already expired is a 400, the same rule as creating one: nothing re-issues a dead credential.
- The 50-key cap counts **live** keys, so expired keys free their slot (they are already refused by the lookup). Counting them would let a customer's own expiries lock them out of the cap with nothing left to revoke by hand.
- No maximum lifetime: the API takes what the caller asks for. A policy (e.g. 90 days) belongs in the console, not in a hidden server rule.
- **The gateway needs two changes** (it is not this task's code; both measured against the running stack, not guessed): the `api-keys` route predicate has no room for a third path segment, so `/rotate` answers 404 at the gateway until task C adds it, and `ApiKeyAuthenticationManager` must carry `expiresAt` in its cached `Lookup` and refuse an expired one, or a key outlives its expiry by up to the 60 s cache TTL (measured: 200 through the gateway 20 s after expiry while the service's own lookup already said 404). Both are exact in §12.
- Not built: `last_used_at` on keys (a write on the request path, or a throttled writer) — §13.
**Money made visible 2026-10-05** (task D; the money machinery was already tested, none of it was readable): a member reads their own organization's balance and usage, and an operator checks the books on demand. Deviations, on purpose:
- `GET /billing/organizations/{id}/balance` (billing library + billing-service) answers with `BalanceOut` plus `noCredit`, the flag the gateway actually reads for its 402. `GET /usage/organizations/{id}/summary?from=&to=&groupBy=model|day&limit=` (usage library + usage-service) answers with the tokens and the cost in micro-BRL per group; the cost is priced with `Price` (the record and its `cost`, in the `billing` library so both services use one arithmetic) and the price history from `GET /billing/prices` (internal, no gateway route), so the price row and the rounding are the ones the debit job bills with, and a row no price covers is `null` rather than a number nobody set.
- Authorization for both, the same rule: `id-account` (the gateway sets it, inbound copies are stripped) must be a member of the organization in the path, checked with organization-service's `GET /organizations/{id}/members/{idAccount}`. No header at all is 401, and a non-member gets back the same 404 organization-service gives, so an endpoint never confirms that another organization exists and never shows its numbers. Never "my balance" by ambient identity, never a list of organizations; changing money stays internal (`POST /billing/grants`).
- `GET /actuator/reconcile` on billing's management port (8081, never published, never routed) runs the same pass as the scheduled reconciliation: it re-syncs every `no_credit` flag, never fixes a balance, and answers per organization with the balance, the ledger sum and whether they agree (drifted rows first, at most 100, counts over all). `docker/revenue-check.sh` calls it through the internal network and exits non-zero when the books disagree.
- **The gateway routes this needs are task C's** (`api/gateway-service/src/main/resources/application.yaml`, in `spring.cloud.gateway.server.webflux.routes`; both `Method=GET`; the default security chain already requires a JWT and IdentityHeadersFilter already sets `id-account`, so no filter or extra config): id `billing-balance`, `uri: http://billing:8080`, `Path=/billing/organizations/{id}/balance`; id `usage-summary`, `uri: http://usage:8080`, `Path=/usage/organizations/{id}/summary`. Until they exist both endpoints are reachable inside the network only, which is the safe default.
- The summary prices per (model, mode, UTC day), not per billing window: one priced row per 5-minute window is thousands per model per month (267k with compose's 10 s windows). ponytail: per-window pricing once the history read or the history itself needs bounding. The ceiling: a price that changed inside a day misprices that day's earlier tokens, and per-day rounding can differ from the per-window charge by under 1 micro-BRL per window (the charge itself stays exact in the ledger). The summary leaves our own failures (`status=error`) out, like the seal job leaves them out of a billed window, so it agrees with `GET /usage/totals` only while nothing failed — `totals` counts them on purpose, for the engine reconciliation. Its tokens come from `usage_event` by arrival, so the last minutes show up before their window is sealed; more groups than `limit` or a range over 31 days is a 400, never a silent truncation.
- What moving `Price` into the library bought: one implementation of the rounding and one of the "row in effect" rule (`Price.at`), instead of a SQL-shaped one in billing and an in-memory one in usage; and the deletion of a positional quote contract (`POST /billing/quotes`, at most 2000 rows, `QuoteIn`/`QuoteOut`/`TokenSum`/the caps). It did **not** remove the call between the two services, and no design that keeps the summary in usage-service can: the price table is billing's schema. **The call stays, deliberately** (2026-10-05, reviewed): usage-service reads the price history (`GET /billing/prices`: append-only, a row per price change, nothing to cache) while billing pulls sealed windows from usage. No money is computed in the caller, and because compose's `depends_on` cannot express a cycle, usage's dependency on billing is deliberately absent: a summary taken while billing is down still answers the tokens, with the cost `null` (WARN, ids only). The alternatives are worse and rejected: serving the summary from billing-service inverts ownership (the summary belongs with the usage data), duplicating the price table creates a second money source, and replicating prices is a cache whose staleness is a money bug.

**Phase 6 built 2026-10-03** (log: [phase-6-progress.md](phase-6-progress.md)): batch-service (schema `batch`) serves OpenAI's Files and Batch API through the gateway: upload a JSONL file, create a batch, poll it, cancel it, read the output and error files. A worker runs each line through inference-service with the batch's identity and a `batch-line` marker: priority 30, no rate buckets, only while the model is at most half busy, credit checked per line, priced at half the sync price. A line keeps one usage event id and start, so a line run again after a crash is billed once. Exit check on the RTX 3050 (`docker/batch-bench.sh`): a 10,000-line batch completed in 999 s (10.0 lines/s) beside enterprise traffic at 100% goodput (TTFT p95 80 ms) while trial was shed; batch-service was SIGKILLed mid-call halfway, the cut line ran again, and usage-service held exactly 10,000 events, each the run that answered; no TTFT timeouts. Found on the way, both in inference-service's usage reporter since phase 2 (= unbilled usage), both fixed with a regression test: concurrent reports were dropped (`FAIL_NON_SERIALIZED` on a unicast sink), and a usage-service slower than 1 s killed the reporting pipeline for good (`bufferTimeout` flushing without demand → `OverflowException`; now `fairBackpressure`). Also: a batch line cut short by a crash was billed for its partial run while its answer went free; now only the run that answered is billed. Deviations, on purpose:
- Files live in Postgres (`bytea`), capped by the gateway's 4 MB `/v1` body limit (OpenAI allows 200 MB); object storage when files grow or hosting is decided.
- A batch file is validated when the batch is created (400 naming the line) instead of OpenAI's asynchronous `validating` → `failed`; no list endpoints, no `metadata`.
- Batch lines take only idle capacity, the same share as trial (C/2), FIFO across batches; no per-organization fairness between batches yet.
- Usage event ids are name-based UUIDs from the JDK (v3, MD5) instead of v5; a batch event's `started_at` is the batch's creation time, so the partitioned primary key `(event_id, started_at)` catches a re-run.
- A batch line reports usage only for the run that answered: a failed or cut-short run (batch-service died mid-call) runs again or isn't billed at all. Otherwise the first event in with the line's id wins, and a crash bills the partial run while the answer goes free (found by killing batch-service mid-call).
- Closing an organization or erasing an account doesn't delete its batch files yet: they expire after 30 days (the erasure saga is phase 7). A revoked key or a suspended organization doesn't stop a running batch; only credit is checked per line.

**Phase 5 built 2026-10-03** (log: [phase-5-progress.md](phase-5-progress.md)): inference-service admits each chat request before the engine: rate buckets per organization and model in Valkey (requests, input tokens, output tokens per minute; one Lua script; settled with real counts at the end), then in-flight caps in memory (trial half of C, standard 85%, enterprise C + q; plus a cap per organization), held until the response ends. Refusals are immediate 429s with `retry-after`/`retry-after-ms` (codes `rate_limit_exceeded`, `model_busy`); answers carry `x-ratelimit-*` headers. Bench through the gateway on the RTX 3050 (`docker/bench.sh`, three tiers at once): enterprise goodput 98% at C = 4 (TTFT p95 ≤ 351 ms), trial 429 p95 ≤ 16 ms (max 91 ms), no TTFT timeouts. Deviations, on purpose:
- Limits are per tier, applied per organization and model; no "model class" axis while there are two models.
- Buckets are checked before the caps, so a request refused by a cap still counts against the buckets (OpenAI counts unsuccessful requests too) and the cap is taken with no async gap before the engine call.
- q = 2 on vLLM (phase 3: a longer queue pushes TTFT p95 past 2 s); `--max-num-queued-reqs 8` stays as the engine-side backstop.
- No engine health-check loop: a dead engine already answers 503 within ~2 s (1 s connect timeout, one retry).
- No dashboards or admission metrics yet; they come with the observability stack (platform.md). The bench prints the numbers.
- Rate-limit headers cover requests and input tokens (OpenAI's names); no `x-ratelimit-reset-*`.
- The bench uses curl workers, not `vllm bench serve`: a second torch process beside vLLM, llama.cpp and nine JVMs ran the 7.6 GB Docker VM out of memory.
- The gateway's flood brake still answers 429 with an empty body on `/v1` (not OpenAI-shaped).

**Phase 4 built 2026-10-03** (log: [phase-4-progress.md](phase-4-progress.md)): billing-service (schema `billing`) bills sealed usage windows into an append-only ledger in micro-BRL, keeps a per-organization balance in the same transaction, and flags `no_credit:{org}` in Valkey when `balance + credit_limit ≤ 0`; the gateway answers `/v1` with 402 `insufficient_balance` while the flag is set. Credit comes from an internal grant (`POST /billing/grants`, idempotent). usage-service gained `GET /usage/windows/next?after=` for the debit job. Deviations, on purpose:
- Append-only is enforced by triggers (UPDATE/DELETE/TRUNCATE refused on `ledger_entry` and `price`; new prices must start in the future), not by a second DB role: one DB user in the prototype. Roles when a shared DB exists.
- No customer-facing balance endpoint (no console yet); the smoke test reads balances with psql.
- Compose runs 10 s usage windows (2 s grace, debit every 2 s) so billing shows within seconds; service defaults stay 5 min / 60 s.
- A new organization can call `/v1` until its first debit (no balance row, no flag); the overshoot is at most one window of usage. Trial credit on org creation is a later decision.
- Flags are synced after every debit and grant, plus a reconciliation every 10 min that re-syncs all flags and logs (ids only) any balance that differs from the sum of its ledger; it never fixes anything itself.
- Seeded prices are placeholders, not commercial prices.

**Pass 2 decided 2026-10-07** (the grilling outcome `together-baseten-grilling-outcome.md` and ADRs 0001 and 0002, kept in the project's `work/research` and `docs/adr`, outside this repository): the next bar is "launch-ready", passing a scorecard on a simulated fleet with no GPU spend: load (2,000 concurrent streams and 200 requests per second over at least 3 gateway and inference replicas and 8 simulated engines, our added latency at most 50 ms p99, no errors beyond injected faults), faults (kill any one container mid-load: no lost and no double-billed usage event, a bounded error window), fairness (a trial flood moves enterprise TTFT p95 by at most 10%), metering (reconciliation inside tolerance after every drill), restore (a backup restored gives identical ledger totals) and a rolling restart under load that fails no request. Thirteen decisions follow from it, the ones this document now builds on: in-flight capacity is shared across replicas by slot leases in Valkey, not by an external router (ADR 0001); a lease takes one slot plus a token weight checked against a per-replica budget read from the engine; a request takes the better of two random replicas; with Valkey down each replica admits against its fair share, never the full per-replica caps and never a refusal; no reserved capacity per organization; overshoot after credit runs out is accepted, published as lag gauges and stated in the terms as a duration; batch files go to S3-compatible storage, 7 days by default, 30 at most; there is no CPU engine, development and CI run a simulated engine (ADR 0002); Kubernetes and autoscaling are the next pass, this pass only publishes the scaling signals (tokens in flight, waiting requests, KV usage). Embeddings, rerank, vision, audio and the Responses API stay out.

**Slot leases built 2026-10-08** (ADR 0001; I3 and I5 of pass 2, log: [pass-2-inf-progress.md](pass-2-inf-progress.md)): the in-flight caps are no longer counted in each inference-service JVM. A request takes a slot lease from one Lua script in Valkey (`lease-take.lua`, the pattern of the rate buckets: Valkey `TIME`, one hash slot per model through the `{model}` tag). A lease is the member `<token weight>:<uuid>` of the sorted set of its engine replica (`lease:{model}:<n>`) and of its organization's (`lease:{model}:org:<id>`), scored by its expiry in milliseconds. The script drops expired members, refuses when the fleet is at the tier's share of the sum of the replicas' slots (enterprise: slots plus queue places), when the organization is at its `max-in-flight`, or when no replica has a free slot (a free queue place only when none has a slot); it then takes the better of two random replicas by the lower used fraction of the token budget (the sum of its leases' weights, `estimated input + max_tokens`, against the KV cache in tokens read from `vllm:cache_config_info` `kv_cache_size_tokens` at startup, or the configured `kv-tokens`, and the log says which; an empty replica takes any request), looks at the other candidates before it refuses for want of token room, and writes the lease with the key's expiry set (ttl plus one second) on both sets. The holder renews it every third of `carmonai.inference.lease-ttl` (30 s) while the request runs; release deletes that member only (`lease-release.lua`), so a double release and a release by a holder whose lease expired change nothing; a holder that dies frees its slots within one ttl; a set nobody asks about again expires by itself. With Valkey down each inference-service replica admits against `slots / carmonai.inference.expected-replicas` from the leases it holds, raises `carmonai_inference_lease_store_unavailable`, logs once per outage, and puts its leases back by renewal when Valkey answers (`lease-renew.lua` writes the member whether or not it is still there; `lease-load.lua` only reads the weight in flight per replica, for the scaling signals). Tier shares, `max-in-flight`, the bounded wait and VTC ordering are as before, now over fleet totals. Deviations, on purpose: (1) a queue of 0 is valid (slots >= 1, queue >= 0); (2) the VTC counters stay per inference-service replica (ADR 0001 keeps leases to capacity, not ordering); (3) the token budget is read once per start, so an engine restarted with another cache size needs a restart of the service; (4) leases lost with Valkey (a restart or failover that drops recent writes) are written back by the holders' next renewal, within a third of the ttl; until then the engine's own `--max-num-seqs` and queue limit bound the over-admission. **Gateway: rolling restart and breakers built 2026-10-08** (G1 and G2 of pass 2; log: [pass-2-gw-progress.md](pass-2-gw-progress.md)): on SIGTERM `ShutdownDrain` (a lifecycle phase just before the web server's graceful phase) makes the gateway go not-ready at once (`:8081/actuator/health/readiness` answers 503) and refuses new requests with 503 `server_draining` (`retry-after: 1`, `retry-after-ms: 1000`, `connection: close`, OpenAI-shaped) for `carmonai.gateway.drain-delay` (10 s, longer than a balancer needs to see the probe), then Reactor Netty closes the listener and waits for running requests, at most `spring.lifecycle.timeout-per-shutdown-phase` (660 s, the longest request the gateway promises to finish); the management port closes after that, so the probe answers 503 for the whole drain. The runtime must grant 10 + 660 s plus margin: `stop_grace_period: 720s` (Kubernetes `terminationGracePeriodSeconds: 720`); compose does not set it yet. Each of the two breaker routes (`inference`, `batch`) has its own named Resilience4j breaker, counts only what proves the hop sick (refused or hung connects, premature close, response timeout, an upstream 504) and passes an upstream 500, 502 or 503 through untouched, because the breaker is shared by every tenant on the replica and one tenant must not be able to open it for all; slow successful calls never count (slow-call threshold 700 s, above the 660 s route timeout); a route `response-timeout` or an upstream 504 is the gateway's own 504 `upstream_timeout`. The starter's own 25-call bulkhead is switched off: `RouteBulkheadFilter` is the bulkhead, per route from the route metadata `max-concurrent` (64 inference, 16 batch), held until the answer has been written, and over it a call gets 429 `gateway_busy` and never reaches the breaker. Corrections found on the way: the breaker as the YAML shortcut built it was named `name=inference` with no fallback; the starter's bulkhead counted as a breaker failure. Deviations, on purpose: a failure after the response headers (a stream cut half way) is not seen by the breaker; the breakers are per replica, in memory.

**Gateway request path hardened, bodies stream built 2026-10-08** (R1 and R1c, repair of G2): the `/v1` checks (4 MB cap, no Transfer-Encoding, no HTTP/1.0, no key in the URL) decide what is `/v1` with the matcher the API-key security chain is built on, so percent-encoded and `;`-parameter spellings of a path are judged exactly as the router and the chain judge them (`OriginFilter` too), and the 4 MB cap is also enforced on the bytes read, not only on `Content-Length`. The circuit breaker does not count a client's bad upload, the gateway cuts a request body that stops coming (`carmonai.gateway.request-body.read-timeout` 10 s between reads, `timeout` 60 s in all; two properties feeding a `NettyServerCustomizer`, because Boot 4.1 has none), and the two `/v1` routes have no `fallbackUri`: request bodies stream to the upstream and are never held in memory (Spring Cloud Gateway's body cache costs per network read, so no slot count can bound it), and the open-breaker, timeout and counted-504 answers are written by the error path (`UpstreamFailureHandler`). A route permit is taken before the body is read; one organization may have only `upload-share` bodies arriving at once on a route (8 inference, 4 batch; `UploadShareFilter`), so idle or slow uploads cannot fill a route for the others. Deviations, on purpose: a flood from many organizations can hold a route's permits for up to the 60 s request timeout (429 `gateway_busy` for the rest); `request-body.timeout` is global and must be re-derived when the files cap is raised; the 408 of a stalled body is best effort. New stores of personal data: none; the request body is forwarded as it arrives and never held, written, logged or cached.

**Gateway error contract built 2026-10-08** (G3): every response the gateway writes itself, whoever produces it, is OpenAI's `{"error":{"message","type","param","code"}}` (`param` null) with `Content-Type: application/json`, an `x-request-id` and, on every 429 and 503, both `retry-after` and `retry-after-ms`. That covers the filters and security chains, Spring's own failures (no route is a 404 `not_found`, a refused method a 405 with `Allow`, an unexpected exception a 500 `internal_error`), an upstream whose name does not resolve (503), and what Reactor Netty answers before WebFlux has an exchange (undecodable request, line or headers too long, bad percent escape: 400, 414, 431), which `MalformedRequests`, a handler in the Netty pipeline in front of `HttpTrafficHandler`, gives a body, a request id and an access-log line. A foreign `Origin` on a session endpoint (login, refresh, logout, register) is a 403 `forbidden_origin`, also for an encoded spelling of the path. `GatewayErrorHandler` answers every failure `UpstreamFailureHandler` leaves and skips only an exchange whose response is already committed; any `IOException` or timeout toward an upstream is the 503 `service_unavailable` (`inference_unavailable` or `batch_unavailable` on the two breaker routes). Answers from an upstream pass through as they are. `GatewayErrorContractIT` sends 49 causes as raw bytes and checks the shape, the id, the retry pair, that nothing of the request is echoed and that no log line outside the access log contains it (Reactor Netty's own WARN for an undecodable request, and Spring's `HttpWebHandlerAdapter` ERROR for an exchange that failed after its response was sent, both quoted the client; the first now logs the exception class, the second logger is off). 499 exists only in the access log: a client that hung up before a status was chosen. Deviations, on purpose: the request id is a header, not a field of the body (OpenAI's shape has none); `MalformedRequests` depends on Reactor Netty's pipeline name `HttpTrafficHandler`; a key lookup or JWKS that is down is a 503 on the console routes too (it was a 401); a method a route declines is a 404; the error pages of the edge proxy are not covered (they need `error_page` with the same JSON). New stores of personal data: none; the error bodies are fixed strings.

**Gateway flood brake, state across replicas and upstream balancing built 2026-10-08** (G3b, G4, G5): the per-caller token buckets (`RateLimitFilter`, Valkey hashes `rl:gw:key:<keyId>`, `rl:gw:account:<accountId>`, `rl:gw:anonymous:<ip>`, 120 s after the last call) are properties, `carmonai.gateway.rate-limit.key|account|anonymous` with `burst` and `per-second`, and the key bucket is derived from the biggest tier of inference-service so the flat brake never refuses a key before the tier does: 6000 at once and 100 a second (it was 20 and 10), twice the enterprise tier's 3000 and 50 because the brake also counts calls the tier does not; a test fails when it falls under the biggest tier. The brake is a backstop against floods, the quota is the tier. The gateway keeps no cache of keys or credit in its own memory: the lookup `apikey:{hash}` (60 s), billing's `no_credit:{organization}` flag and the brake buckets are Valkey's and shared by every replica, so a revoke and a credit change reach all replicas at once and a key's expiry is exact; what each replica keeps is the JWKS, the route permits and upload shares, the circuit breakers and the local brake buckets that take over when Valkey fails. Valkey away is a documented degraded mode: `/v1` fails closed (503, `Retry-After: 5`, after the 1 s command timeout), console routes stay up and the brake fails open into one bucket per replica (N replicas admit N times the rate), and the gateways serve again within about 2 s of Valkey's return because Lettuce's reconnect delay is capped at 2 s (its default grows to 30 s). A name with several replicas behind it is balanced per request by the gateway itself (`ReplicaSpread`): Reactor Netty dials the first address of the resolved list, caches it for the record's TTL (Docker says 600 s) and pools by name, so the shipped gateway sent every request to one inference replica; now the HTTP client opens a connection per request (`httpclient.pool.type: DISABLED`), trusts a DNS answer for `carmonai.gateway.upstream.dns-cache-ttl` (5 s) and starts each connection one address further along the list. The calls to auth-service use a pool of 32 connections that live 5 s, and the JWKS fetch has a pool of its own (2 connections), so a flood of unknown API keys cannot stop console JWTs validating. Deviations, on purpose: no circuit breaker around the Valkey calls (each call pays the 1 s timeout while Valkey is away); one TCP connection per request caps a replica address at about 470 requests per second on a default ephemeral port range; no health checking per replica (only an orchestrator that takes unready replicas out of DNS makes readiness count); the five Feign clients between services keep their fixed `url=` and can pin a replica for the JVM DNS-cache window (30 s), so the SKILL's "replicas scale horizontally" holds for the gateway hops and for a service behind a balancing Service, not yet for every Feign hop; per-key limits that follow a customer's plan are deferred (LAT-04). New stores of personal data: none new; `rl:gw:anonymous:<ip>` holds a client IP for 120 s (erases itself, not exported), and the access log (client IP, ids, 184 days, Marco Civil art. 15) is the one store that outlives an erasure, by legal duty.

**Identity, pass 2 built 2026-10-08** (N0, N1a, N1b; log: [pass-2-idn-progress.md](pass-2-idn-progress.md)): API-key revocation evicts the gateway's Valkey entry after the database commit (`afterCommit`), so a rotation can no longer leave the old key cached by a lookup that raced the transaction; Valkey is deleted before the commit as well (a failure rolls the rotation back) and a failure after the commit is logged, not thrown (the entry then ends with its 60 s TTL). The roles of an organization are one closed set, `owner`, `admin`, `member`, as the `Role` enum in the `organization` library: a value type whose predicates (`managesKeys()`, `closesOrganization()`, `managesMembers()`, `managesOwners()`) are the authorization table, its lowercase constants being the wire and column words, so no service keeps a role name. Refusals are specific exceptions with a stable `code` in the problem body (`owner_required`, `last_owner`, `manager_required`, `organization_not_active`, `key_limit_reached`, `already_member`). organization-service manages members: owners and admins add an existing account by email (the internal `POST /accounts/lookup` of account-service resolves a verified email to an id; an unknown and an unverified email answer the same plain 404), change roles and remove members; any member can leave; only an owner grants or touches `owner`, nobody raises their own role, and an open organization always keeps one owner on remove, demote, leave and erasure, counted under the row lock of the organization (409 `last_owner`). The member endpoints are built and not routed by the gateway (LAT-01, D-45): an operator adds colleagues by hand. Deviations, on purpose: no invitations (SMTP waits), so an add is unilateral (always as a `member`) and a later promotion by an owner can leave the target as sole owner of an organization they cannot leave, so their erasure answers 409 `last_owner` until they close it (threat model 3b of the log); `OrganizationService.addMember` sees the Feign `ResponseEntity` of the lookup, as other services already do; no database guard for the last owner (the lock is the guard).

**Batch files in object storage built 2026-10-08** (B1 and R2 of pass 2; log: [pass-2-bat-progress.md](pass-2-bat-progress.md)): batch-service keeps file content in an S3-compatible bucket through one class, `Bucket` (AWS SDK v2, Apache5 client), and Postgres holds metadata only (`V2026.10.08.001__object_storage.sql`); the object key is `<organization>/<file id>`, input, output and error files alike, and nothing is held whole in memory (an upload is streamed as 8 MiB multipart parts, size and SHA-256 taken on the way; batch creation validates the file as a stream and stages the valid lines to a temp file). **Metering integrity built 2026-10-08** (U1 to U3 of pass 2, no log of its own): seal and debit are safe on several replicas (two instances sealing the same window seal it once, two debit calls bill every sealed window once and leave `balance == sum(ledger)`, an instance killed between the ledger write and the cursor cannot double-bill), the seal decides by the database clock, not the JVM's, and the credit flag is re-synced from the balance after every debit, grant and adjustment. Deviations, on purpose: the gauges refresh on Spring's scheduler (one shared thread), so a job that holds it freezes them for as long as it runs; the bound ignores the run time of the jobs and covers no backlog after an outage.

The daily retention sweep (`AccountRetention`, `carmonai.account.sweep-cron`, default `0 41 3 * * *`, `-` switches it off) erases accounts never verified within `carmonai.account.unverified-retention` (7 days, refused below 24 h) with their links, and deletes expired links, in batches of `sweep-batch-size` (500, 1 to 1000) for at most `sweep-max-batches` (20, 1 to 100) per run, each batch one DELETE over rows locked with `FOR UPDATE SKIP LOCKED` so any number of replicas can run it (`V2026.10.15.001__retention.sql` adds `account.created_at`); verified and provisioned accounts are never touched. Batch files expire `carmonai.batch.file-retention` (7 days, at least 1 minute) after they are written.
- **Money (BE-06, BE-25).** `POST /billing/grants` takes a `type` (`grant`, the default, or `top_up`) and a `reference` (at most 256 characters, never a payer's name: the ledger is append-only); the idempotency key (`grant:{org}:{key}`, for a Pix top-up the end-to-end id) is a promise about content: a replay with the same amount, type and reference is a 200 and writes nothing, any other content is a 422 `idempotency_conflict` and writes nothing (IETF draft-ietf-httpapi-idempotency-key-header, section 2.7). The ledger is corrected by signed entries, never edited: `POST /billing/adjustments` (`AdjustmentIn{organizationId, amountMicroBrl, type, reference, idempotencyKey, allowNegative}`) writes one ledger row of type `adjustment` or `refund` under `adjust:{org}:{key}` and moves the balance in the same transaction, with the idempotency of the grant; an entry that would leave the balance below 0 is a 409 `balance_would_be_negative` and is rolled back unless `allowNegative` is true (the check reads the balance row the entry has locked, so two refunds at once cannot both pass); the gateway flag follows the new balance. The operator procedure is the runbook `refund`; `ops/adjust.sh` is SELL-04.
- **The API (BE-05, BE-12).** A parameter that changes the answer and that the engine path does not honour is refused, not dropped: `response_format` other than `{"type":"text"}`, `logprobs` other than false, any `top_logprobs`, any `logit_bias` answer 400 `unsupported_parameter` naming the field, before the first byte (also with `stream:true`) and before admission, so no engine call and no usage; a JSON null is an unset field; `user`, `metadata`, `store`, `top_k`, `min_p` and `reasoning_effort` stay ignored (not in the allowlist). `GET /v1/models/{id}` exists (inference `GET /v1/models/{*id}`, the gateway route `/v1/models/**`; an unknown id is the same 404 `model_not_found` a chat request gets, the id not echoed); a model id may contain a slash and current OpenAI SDKs send it as `%2F`, so the gateway's strict firewall allows the encoded slash for `GET /v1/models/...` only, every other check unchanged for that request. A streaming client that sets `stream_options.include_usage` sees `usage: null` on every chunk and one final chunk with `choices: []` and the usage, the engine's own, from which the usage event is also written; without the option it sees no usage (the engine is still asked for continuous usage, billing needs it). The engine's reasoning is returned as `reasoning` and `reasoning_content` and billed inside `completion_tokens`. `max_tokens` above the model's `max-output` is a 400 `invalid_max_tokens` naming the cap.
- **Error bodies and the database (BE-21).** No error body of any service carries the text of an exception (CF-04). A refusal carries a code and the Resource writes the sentence for that code: account-service `Refusal.Why` (name, email, password, link, page) and a literal for the unverified-email 403; auth-service `manager_required`, `organization_not_active`, `key_limit_reached` and the input checks `invalid_name`, `invalid_expires_at`, `invalid_page`; organization-service `owner_required`, `last_owner`, `manager_required`, `organization_not_active`, `cache_eviction_failed`, `organization_limit`, `already_member` and a plain "the request is invalid"; billing-service and usage-service 400 `invalid_request` and constants for the 422 and the 409. An `IllegalArgumentException` from the JDK or a library answers "the request is invalid" (a malformed `page` used to come back as `For input string: "..."`), the framework's own refusals and 500 carry no request text, and a downstream 4xx is relayed as the body the other service wrote (its own fixed text) while a downstream failure is a bare 503; a canary test in every handler path pins this. Every database-backed service's JDBC URL (account, auth, organization, billing, usage, batch) carries `options=-c statement_timeout=5000`: Postgres cancels any statement, Flyway's included, after 5 s (SQLSTATE 57014); a migration that needs more must set `SET LOCAL statement_timeout = 0`, and a pooler between the services and Postgres must list the startup parameter (`ignore_startup_parameters`) or the setting moves to `ALTER ROLE`. Erasure of an account (`DELETE /organizations/members/{idAccount}`) locks the organizations the account owns in id order before it reads any membership, so two co-owners erased at once cannot deadlock (100 concurrent rounds in the test). A key rotation or revocation by a member is a 403 before the key is looked up (CF-07). A read from the bucket without `Content-Length` is a read of unknown length (`Bucket.Content.UNKNOWN`) and the file-content endpoint then answers chunked (CF-12). Startup errors name the model and the replica's place in the list and never an engine url (CF-02).
Deviations, on purpose:
- BE-11: trust in `X-Forwarded-For` is opt-in by peer network and the last entry is taken, where the guide said `framework` strategy; HOST-06 and HOST-08 set `CARMONAI_GATEWAY_TRUSTED_PROXIES` to the edge container's fixed address only after port 8080 is no longer published (a whole-subnet value would let a caller NAT-ed through the published port forge the header).
- BE-23: a property replaces "omit the routes from the production config" (a profile cannot subtract list entries); the safe value is the profile's, so a deployment without `SPRING_PROFILES_ACTIVE=prod` shows batch and accepts `cmn_test_` keys with nothing failing or logging; HOST-06 sets the profile and the check is the `curl` that must print 404.
- BE-24: the guard class is copied into four services (a shared library would need a decision on what a library may hold: libraries hold Feign interfaces, records and at most a value type).
- BE-12: the encoded-slash exception on the gateway firewall; the launch alias `carmonai/chat-standard` has a slash (D-06).
- BE-21: `statement_timeout` also cancels a lock wait, so an erasure or admin change that waits for a row lock longer than 5 s fails with a 500 instead of waiting; a promotion to owner that lands during an erasure's lock wait can still be locked out of id order (a `ponytail:` comment names the retry loop).
- BE-02: a floor, not a parse of the raw text, so a bare number of 1000 or more is still read as milliseconds and passes.
Not built: BE-13 to BE-17 and BE-19 wait for the first real GPU run (structured output, the production catalog and engine hardening, the engine link in code, limits from the bench, price rows, the cancelled-stream gap), and BE-01's pull requests are the owner's. New stores of personal data: `accounts.terms_acceptance` (above: kept after erasure as evidence, exported) and `account.created_at` (purpose: the 7-day proof of the email; leaves with the account); no other step adds a store, a log field, a metric tag or a cache entry. Erasure and export of every earlier store are unchanged.

## 1. What carries over from the video, and what doesn't

The video (skill `batch-inference-design`) designs for a toy GPU: one batch at a time, fixed 100 ms, one answer per request. Real engines (vLLM, SGLang, TensorRT-LLM) batch continuously at every token, the KV cache in GPU memory limits concurrency, and answers stream.

| Video idea | Real LLM serving | Carmonai |
|---|---|---|
| Hand-written batcher, 100 items or 40 ms | Engine batches every step, 2–4×+ throughput over static batching | **No batcher in Java** |
| Index demux, futures | One HTTP/SSE stream per request | WebFlux relays each stream |
| Three Redis tier queues | vLLM `--scheduling-policy priority` orders the waiting queue, but a waiting request never evicts running ones; it only preempts running requests short of KV blocks | **Priority + per-tier in-flight caps** at admission; no Redis queue on the interactive path |
| Capacity in requests/s | Capacity in tokens/s; prompt length dominates | Limits and prices in tokens, measured |
| One latency number | TTFT, ITL, end-to-end; goodput | SLOs on TTFT and ITL, goodput as the test pass mark |
| Scale on GPU utilization | Utilization reads busy when healthy | Waiting requests and KV-cache usage (later, >1 replica) |
| Edge 429, shed lower tiers first | Same | **Keep**, in inference-service |
| One retry, then a clean 503 | Safe only before the first token reaches the client | **Retry once on connect error/5xx before the first byte** |
| No DB on the hot path | Same | **Keep**: Valkey lookups and in-memory counters only |
| Batch inference product | Async batch at a discount (OpenAI: 50%, 24 h) | Batch API, phase 6, fills idle capacity at the lowest priority |

## 2. Target architecture

```
client ─HTTPS─> Caddy (the edge, D-26; not built yet) ─> gateway-service replicas (WebFlux)
                           ├─ console routes, JWT ──> account / auth / organization / billing / usage
                           ├─ /v1/files, /v1/batches (hidden at launch) ──> batch-service ──> S3-compatible bucket
                           └─ /v1/chat/completions, /v1/models, /v1/models/{id}, API key ──> inference-service replicas (WebFlux)
                                                         ├─ admission (Valkey buckets, slot leases shared by all replicas)
                                                         ├─ field allowlist, relay SSE, retry before 1st byte
                                                         ├─> engine replicas: simulated engine (dev, CI) | vLLM (GPU; rented, only over WireGuard)
                                                         └─ UsageEvent ─Valkey stream─> relay ─HTTP batch─> usage-service <─pull sealed windows── billing
Valkey: api-key cache · org flags (suspended / no credit) · rate buckets (inference) · flood-brake buckets (gateway) · slot leases · usage stream
Kafka: later, when an event gets a second consumer
```

- **gateway-service** is the edge: credentials, tenant flags, a flat flood brake, routing, the error contract, the drain on a rolling restart. It knows nothing about models. It is stateless (its shared state is Valkey's) and balances each request across the replicas of an upstream itself.
- **inference-service** (new, WebFlux) is the only caller of engines; batch-service uses it too. Gateway filters can't read an SSE body without buffering it, and long streams stay out of the login path, so it is worth the extra hop. It allowlists OpenAI request fields and sets `model`, `priority`, `cache_salt`, `n`, max tokens and `stream_options` itself; admits; relays with a flush per chunk; times TTFT and idle gaps; retries once before the first byte; publishes `UsageEvent`. It treats the body as JSON with a few parsed fields, not Java records for the whole OpenAI schema, and ships no Feign library until a Java caller exists.
- **Engines** run as containers (Python/CUDA, or the simulator in Go). Java never runs a model. A model has one or more engine replicas (a static list, `carmonai.inference.models[].replicas`; a restart adds one); a request takes the better of two random replicas that have room, by the lower used fraction of the replica's KV token budget (`Leases`, §7). There is no engine health loop and no failover to a second replica yet: a dead replica that is picked fails the request (retried once on the same one). The llm-d router / Gateway API Inference Extension replaces the picker on Kubernetes.

## 3. One streaming request, step by step

1. **Gateway, credentials**: `Authorization: Bearer cmn_live_…` → prefix and checksum check (no I/O for garbage; a key whose prefix this deployment does not issue, `carmonai.gateway.key-prefixes`, is a 401 at once) → SHA-256 → Valkey `apikey:{hash}` → {key, org, org status, tier, expiry}; miss → auth-service → cache 60 s (the operator's tier or status change, a revoke and a close delete the entry at once; the 60 s is the bound only when that deletion fails). Unknown, revoked or expired → 401 `invalid_api_key`. Valkey down → 503 with `Retry-After` (fail closed, so clients don't think the key died).
2. **Gateway, tenant flags**: org suspended → 403 `organization_not_active`; `no_credit` flag → 402 `insufficient_balance` (not OpenAI's 429 `insufficient_quota`: the OpenAI SDK retries 429s). A new organization carries the flag from its creation until its first grant (BE-09). While `carmonai.gateway.batch-enabled` is false, `/v1/files...` and `/v1/batches...` are a 404 before any of this.
3. **Gateway, flood brake**: a token bucket per caller in Valkey, shared by the replicas (`RateLimitFilter`, `rl:gw:key|account|anonymous:…`, a Lua script; sizes are `carmonai.gateway.rate-limit.*`: 6000 at once and 100 a second per API key, 20 and 10 per console account, 20 and 1 per client address on login and register). It is a backstop against floods: the quota is the tier in inference-service. It fails open into a local bucket per replica while Valkey is away (inference-service admission still protects the GPU). The client address is the TCP peer unless the peer is a trusted proxy (BE-11).
4. **Gateway → inference-service**: only `/v1/chat/completions`, `/v1/models` and `/v1/models/{id}` (the id may carry a slash, sent raw or as `%2F`; the strict firewall allows the encoded slash for that one GET). Before auth, `/v1` rejects with 400 any `Transfer-Encoding`, HTTP/1.0, or a query string carrying `cmn_`/`key`/`token`, judged on the decoded path; no CORS on `/v1`. Strips `id-account`, `id-organization`, `id-api-key`, `tier`, `x-internal-token`, `Cookie`, `Forwarded`, `X-Forwarded-*`, `traceparent`, `tracestate`, `baggage` on every route and sets the identity ones from the principal; sets `X-Request-Id`; removes `Authorization`; requires `Content-Length` ≤ 4 MB (411/413, also enforced on the bytes read; the body streams to the upstream and is never buffered). Route metadata `response-timeout: 660000` (the gateway only times the wait for headers, which inference-service sends with the first token), `max-concurrent` (64: a call over it is a 429 `gateway_busy`) and `upload-share` (8 bodies arriving at once per organization). Whatever goes wrong, the answer is OpenAI-shaped with an `x-request-id` (the error contract), and a draining gateway answers 503 `server_draining`.
5. **inference-service, request**: unknown `model` → 404; `n` > 1 → 400; body > context × 16 bytes (128 KB at 8k) → 413; max tokens = `max_completion_tokens` else `max_tokens`, absent → model max, above it → 400. Field allowlist: drops client `priority`, `request_id`, `kv_transfer_params`, `vllm_xargs`, `structured_outputs`/`guided_*`, `chat_template*`, `prompt_embeds`, `echo`, and ignores `user`, `metadata`, `store`, `top_k`, `min_p`, `reasoning_effort`; a parameter that changes the answer and that the engine path does not honour is refused, not dropped: `response_format` other than text, `logprobs` other than false, any `top_logprobs` or `logit_bias` → 400 `unsupported_parameter` naming the field, before the first byte and before admission; message content is text only (no `image_url`, audio or file, so the engine never fetches a URL). Sets `priority` from tier, `cache_salt` = per-org secret (no cross-tenant prefix-cache timing), `stream_options {include_usage, continuous_usage_stats}`. Upstream headers are built from scratch, never copied. Tool calls are returned to the client, never executed.
6. **inference-service, admission** (§7): one Lua script on Valkey debits rpm, input tokens (estimate = body bytes ÷ 4) and checks output budget; then a slot lease (`lease-take.lua`): the tier's share of the fleet, the organization's `max-in-flight`, a replica with room for the token weight. A paying tier waits up to `carmonai.inference.admission-wait` (1.5 s) for a slot, in the order of its organization's virtual token counter; trial, flex and batch lines are refused at once. Any failure → 429 `rate_limit_exceeded` or `model_busy` with `retry-after`, `retry-after-ms`, `x-ratelimit-*`. Valkey down → skip buckets, and admit against the replica's fair share of the slots (`slots / expected-replicas`). An engine that cannot be reached after the one retry is a 503 `engine_unavailable`.
7. **Relay**: own `ConnectionProvider` (maxConnections = pool cap, `pendingAcquireTimeout` 1 s → 503, `maxIdleTime` 4 s under vLLM's 5 s keep-alive). Timeouts: connect 1 s, TTFT 30 s, idle between chunks 30 s, all under the edge's read timeout. Connect error or 5xx before the first byte → one retry; TTFT timeout → 503 (overload, don't retry); after the first byte → `data: {"error":{…}}` then `data: [DONE]`. Engine 4xx passed through in OpenAI shape; 5xx and engine 401 → 502.
8. **End, error or disconnect** (`usingWhen` holds the resources, `doFinally` finishes): cancel upstream (frees the GPU slot), release the lease, settle token buckets with real counts, publish `UsageEvent` from the last usage seen. Cancelled stream = input + generated output; cancelled non-stream = estimated input only.

Nothing on this path writes to a database.

## 4. Object models

**Tenancy and credentials** (phase 1)
```
Organization  id · name · status(active|suspended|closed) · tier(trial|standard|enterprise, default trial)
Membership    org_id + account_id · role(owner|admin|member, the `Role` enum of the organization library); creating an org makes the creator owner
Acceptance    account_id · document(terms|privacy) · version · accepted_at · channel(pilot_contract); append-only, no foreign key, no name or email; survives erasure, is exported (BE-08)
ApiKey        id · org_id · name · hint(last 4) · secret_hash(SHA-256) · created_by(null after erasure) · created_at · expires_at · revoked_at
              format cmn_live_ (production) or cmn_test_ (any other environment; production rejects it before lookup; the prefix is `carmonai.keys.prefix`)
              + 43 base62 (256 bits) + 6-char CRC32; shown once; ≤ 50 live per org (expired keys don't count); owner/admin create
              expires_at null = never; rotation = one call (new key issued, old key revoked, same expiry)
Session       id · account_id · token_hash · created_at · last_used_at · expires_at      ← with the console SPA
```
- SHA-256 without pepper: a 256-bit random secret can't be brute-forced, and a pepper can't be rotated without reissuing keys.
- `last_used_at` comes from UsageEvent, never written by the gateway.
- Refresh cookie `__Host-carmonai-rt` (HttpOnly, Secure, SameSite=Strict, Path=/) set by auth-service, value `{id}.{secret}`; refresh = conditional UPDATE, hash mismatch on a known id = reuse → delete the row. Gateway checks `Origin` on POST `/auth/login|refresh|logout`.
- Services check membership by calling organization-service per console request, no cache; `/v1` never does.
- Later: invitations, email verification, roles with the owner lock (`SELECT … FOR UPDATE` on the org), password reset, login delay, DPA gate.

**Metering and money** (phases 2 and 4)
```
UsageEvent   v=1, JSON, additive changes stay v1
             event_id(UUIDv7 minted at admission; batch: UUIDv5(job, line)) · request_id · org_id · api_key_id
             · model · mode(sync|batch; batch = the half-price lane: Batch API lines and flex requests) · tier · input_tokens(incl. cached) · cached_input_tokens · output_tokens
             · status(ok|error|cancelled) · started_at · ttft_ms · duration_ms        ← no prompt, output or IP
UsageRaw     partitioned by started_at (day); PK (event_id, started_at); index received_at; 90-day retention
UsageWindow  org · api_key · model · mode · window_start(5 min) · sums                ← sealed by a job
Price        model · kind(input|cached_input|output) · mode(sync|batch) · micro_brl_per_million · effective_from(> now)
LedgerEntry  org · amount(bigint micro-BRL) · type(grant|usage|refund|adjustment|top_up) · reference · idempotency_key UNIQUE
Balance      org · amount · credit_limit
```

## 5. Changes to what is built today

This list was the to-do of revision 2. Items 1 to 9 were done in phases 1 and 2 (the `Origin` check came with the console sessions, the registration answer with email verification), item 10 is settled (Java 25 LTS), and items 6 and 11 below are rewritten for the edge that was decided afterwards.

1. **`RateLimitFilter` bug**: it only recognises `JwtAuthenticationToken`, so every API-key caller would share the anonymous 1 req/s per-IP bucket. Key on the principal's name.
2. **Gateway timeout**: the global 15 s stays for console routes; `/v1` sets 660000 ms in route metadata. Property prefix is `spring.cloud.gateway.server.webflux.*` (the timeouts docs page still shows the old one).
3. **Two security chains**: API-key chain first (`@Order(HIGHEST_PRECEDENCE)`, `securityMatcher("/v1/**")`, `AuthenticationWebFilter` + converter for `Bearer cmn_…` + `ReactiveAuthenticationManager`, failure handler replaced: the default sends a Basic challenge); JWT chain as fallback. JWT on `/v1` → 401; key on console → 401.
4. **`IdAccountFilter` → `IdentityHeadersFilter`**: strips all four identity headers on every route, sets them by principal type.
5. **CSRF**: the "csrf disabled, no cookies" comment stops being true when the refresh cookie arrives; add the `Origin` check then.
6. **Streaming**: Gateway 5.0.3 flushes per chunk for `text/event-stream` and cancels upstream on client disconnect (checked in source); the phase-2 smoke proves it. The edge on `/v1`: no response buffering, a read timeout above the 30 s between events and a response-header wait of 660 s.
7. **Registration enumeration**: `POST /auth/register` answers 409 "email already registered"; fix together with email verification.
8. **Erasure**: deleting an account must remove memberships (409 if sole owner of an active org), delete sessions and null `created_by` on keys — synchronous, idempotent calls in phase 1; the event saga in phase 7.
9. **auth-service gets Postgres** (keys, later sessions).
10. **Java version** ❓: Boot 4.1.1 documents Java 17–26 (checked); 27 is outside and non-LTS. Recommend 25 LTS (also drops the Lombok override).
11. **Edge**: the edge is Caddy, the only published service (decision D-26; HOST-08, not built); the gateway port stops being published once it exists, and the gateway believes `X-Forwarded-For` from the edge only: `carmonai.gateway.trusted-proxies` names the edge container's fixed address (empty by default) and the gateway takes the last entry (BE-11). The edge (HOST-08): Caddy 2.11.7 forwards only the public paths and answers 404 for the rest (`/actuator` included), streams without buffering (`flush_interval -1`), waits up to 12 minutes for response headers (above the gateway's 660 s drain), never sets the server `write` timeout (it would cap whole streams), overwrites `X-Forwarded-For`, and must pass a `%2F` in a path on unchanged (SDKs send a model id with a slash that way; to be proven by the edge checks). Its own 502 and 504 are not in OpenAI's shape and the gateway's error contract does not cover them. Until the edge exists the harness publishes the gateway on `127.0.0.1:8080` only.
12. **Pinned versions with security fixes**: vLLM ≥ 0.26.0 (error-message path leak; earlier DoS fixes), Netty ≥ 4.2.13.Final (request-smuggling fixes). Advisory ids in the review file.

- **Connection**: the engine (simulator or vLLM) is a compose service on the internal network, never published; inference-service reads the engine URL and key from env. vLLM's `--api-key` covers only `/v1`, `/v2`, `/inference`, `/cohere` (`/invocations`, `/pause`, `/abort_requests`, `/update_weights` stay open), so nothing but inference-service may reach the engine — true on the internal network, and a path allowlist becomes mandatory on any remote host.
- **Data rule**: synthetic data only; nothing in the prototype holds real personal data.
- **Rejected free options**: Colab (FAQ bans web services), Kaggle (bans "server farming"), Modal/Lightning (need a card for useful credits), HF ZeroGPU / Studio Lab / GCP trial (can't run our own server). Kept here in case the laptop GPU stops being enough.
- **Laptop numbers are not prices.** They prove the pipeline and size the prototype's caps. Prices come from `vllm bench serve` on the production GPU.
- **Rented GPU (designed 2026-10-11 in the MVP guide, Part 5, decisions D-10 to D-20 and D-23; nothing of it is built).** One server with one 80 GB GPU, count 1, no redundancy (D-12), rented by the hour inside weekday windows 08:00 to 20:00 America/Sao_Paulo, outside which the API answers 503 `engine_unavailable` (D-18); test servers live at most 12 hours (D-17). Providers are tried in the order Latitude in Sao Paulo, a BRL quote, Magalu L40S, then EU, then US (D-19), each with a spending cap (D-17); "served in Brazil" is claimed only if the GPU really is there. The engine is `vllm/vllm-openai:v0.30.0` pinned by tag and digest, model revisions pinned and the weights mirrored in object storage (D-14, D-20), starting values context 32,768, max output 4,096, GPU memory 0.90, prefix cache on, and the slots measured by a ladder against the goodput pass mark (95%, TTFT p95 2 s, TPOT 100 ms; D-15). Customers see one alias, `carmonai/chat-standard`, and the backing model may change with notice (D-06). **The engine is never public** (D-16, D-23): the GPU host dials the control plane over WireGuard point-to-point (not Cloudflare Tunnel, whose 125 s timeout would cut streams); vLLM binds only the tunnel address `10.10.0.2:8000` (Docker ignores ufw for published ports, so the bind address is the protection) and ufw allows 8000, 9100 and 9400 on `wg0` only. The GPU host runs `compose.gpu-host.yaml`: vLLM with `--shutdown-timeout=600` and `stop_grace_period: 660s` so a restart lets a running stream finish, `--api-key` read from the environment, request logging off, and the node and GPU exporters; the control plane uses `compose.remote-engine.yaml` with the model stated in full (`CARMONAI_INFERENCE_MODELS_0_ID`, `_URL=http://10.10.0.2:8000`, `_APIKEY`, `_CONTEXTWINDOW`, `_MAXOUTPUT`, `_SLOTS`, `_QUEUE`; a list is replaced as a whole, so one field alone makes the service exit) and `INFERENCE_REPLICAS=1`. Prometheus scrapes `10.10.0.2:8000/metrics` (job `vllm`; `/metrics` is outside `--api-key`), `:9100` and `:9400` through static targets, and without `/metrics` the revenue reconciliation silently stops. What a remote engine costs the code, read from it: TLS toward vLLM is plain HTTP over the tunnel; there is no engine health loop and no failover; the KV budget is read once at startup; TTFT is measured at the control plane, so the link's round trip is inside every customer-visible TTFT; and a half-dead tunnel holds leases for the 30 s timeout and can fill the tier caps with `model_busy` 429s. The first GPU hour answers what no run has: whether pass-2 admission and leases hold on a real vLLM at v0.30.0 (the metric names and the `vllm:cache_config_info` label come from source reading), the cancelled-stream accounting (a launch gate, D-43), and the real slots. The per-organization `cache_salt` and clamps on `n` and `max_tokens` stay inference-layer work (D-16).

## 7. Admission, fairness, capacity

**Now (any number of inference-service replicas, one or more engine replicas per model):**
- C = highest `--max-concurrency` in `vllm bench serve` that keeps goodput ≥ 95% against the SLOs, per engine replica (`slots`); q = queue backstop (`queue`).
- Slot leases (ADR 0001, built 2026-10-08): the in-flight caps count leases in Valkey, one entry per request with an expiry, not a counter in each JVM, so any number of inference-service replicas see one count per engine replica (the block "Slot leases built" has the script, the keys and the failure modes). Tier caps on the fleet's summed slots: trial 0.5·C, standard 0.85·C, enterprise C+q; plus a per-org cap (`max-in-flight`) so one customer can't fill a tier. This, not engine priority, is what keeps trial from starving enterprise. A lease also carries a token weight (`estimated input + max_tokens`) checked against the replica's KV cache in tokens, read from the engine at startup (`kv-tokens` stands in when it exposes none), and a request takes the better of two random replicas by the lower used fraction of that budget. With Valkey down each replica admits against `slots / expected-replicas`, raises `carmonai_inference_lease_store_unavailable` and admits what its own share allows, so a cache outage does not become a full outage; the engine's own limits are the last backstop. Tier shares, the bounded wait and the VTC ordering stay in our Java code.
- Token buckets `rl:{org:class}:rpm|itpm|otpm` in one Lua script (Valkey `TIME`, one hash slot). Input charged on the bytes ÷ 4 estimate, corrected from usage (vLLM `/tokenize` would be a GPU round trip and isn't covered by `--api-key`). Output takes `max_tokens` at admission and gets back what wasn't generated at the end (built 2026-10-04); buckets and balances may go negative. Overshoot ≤ one request's `max_tokens`.
- vLLM `--max-num-seqs C --max-num-queued-reqs C+q` as the engine-side backstop (it ignores tiers).
- No engine health loop: a dead engine fails the request (one retry before the first byte, then 503 `engine_unavailable`, about 2 s) and the 5 s engine scrape keeps its gauges absent (the laptop GPU sleeps and restarts; that is normal). Failover to another replica needs a second lease; not built.
- Batch: priority 30, smallest cap, backs off on 429.

**Later (Kubernetes, the next pass):** the scaling signals are published (built 2026-10-09, §8: `carmonai_engine_requests_waiting`, `_requests_running`, `_cache_usage`, `_tokens_in_flight` per replica from a 5 s scrape of the engine's `/metrics`); admission does not read them, and a replica stale for 3 s counted as full is not built. Then asymmetric autoscaling (KEDA on waiting / KV / TTFT p95; up fast, down slow, one at a time), node autoscaling, baked weights, min replicas ≥ 1, reserved capacity. Fairness within a tier is in-process since 2026-10-06 (VTC between one replica's waiters); what stays on Kubernetes is the across-replica part (DRR/flow control via GIE/llm-d) and prefix-aware routing.

## 8. SLOs and measurement

- SLOs per model class on TTFT p95, ITL p95, end-to-end p95 (non-stream), availability; goodput = share of requests meeting all of them. Set from phase-3 measurements, revisited on the production GPU.
- Tools: `vllm bench serve` (`--base-url`, `--header`, `--goodput`, `--max-concurrency`) or GuideLLM, run through the gateway with one key per tier. Not Gatling/k6: Gatling's SSE timer stops at HTTP 200 and k6 needs an extension, so neither sees TTFT.
- inference-service records queue wait, TTFT, ITL, whole-request latency, outcome and tokens per model × tier on `/actuator/prometheus` (built 2026-10-06); per-organization numbers stay in usage data, where they belong. Reconciliation compares hourly usage with the engines' token counters (built 2026-10-04: a WARN past max(0.5%, the tokens in flight); the same check on demand at `/actuator/reconcile`; `carmonai_inference_reconcile_mismatch{model}` feeds the alert `ReconciliationMismatch`, which Prometheus and Grafana list: there is still no Alertmanager, so nobody is paged). The metering lag is measured, not guessed: `carmonai_usage_seal_lag_seconds`, `carmonai_billing_debit_lag_seconds` and `carmonai_billing_no_credit_organizations` (no identity tags), and the overshoot bound is the duration `Overshoot.bound` (8 minutes at the defaults). The per-replica scaling signals are in the block "Simulated engine ... scaling signals"; [observability.md](observability.md) lists the dashboards and alerts.

## 9. LGPD, security and abuse

**Roles.** The customer is controller of prompts and outputs; Carmonai is operator. The DPA says: process on instructions only, no training, zero retention for synchronous requests, batch files ≤ 30 days, a sub-operator list with 30-day notice of changes, deletion on termination, incident notice to the customer within 24 h. Carmonai is controller of accounts, billing, access logs and abuse reports. One ROPA table (LGPD art. 37) covers both roles.

**Incidents.** As controller: notify the ANPD and affected people within 3 business days of learning personal data was affected, when the risk is relevant (Res. CD/ANPD 15/2024; small agents get double time unless the processing is high-risk); keep an incident record for 5 years. As operator: tell the customer within 24 h so they can meet their own deadline.

**Content stays in the request** — never in logs, traces, metrics, events, error bodies, caches or dumps:
- Off outside local debug: gateway wiretap, Reactor Netty access log, DEBUG on `reactor.netty`, `org.springframework.web`, `org.springframework.http.codec`.
- Error bodies are fixed text chosen by the error's code, plus the request id (the `x-request-id` header; OpenAI's shape has no id field); never `e.getMessage()` (decoder messages quote the body). Since BE-21 no handler of account, auth, organization, billing, usage or gateway-service reads an exception message, and a canary test (`CANARY-<uuid>` in the message of every handler path) pins each. Engine error bodies are never logged; engine 5xx → generic error.
- OpenTelemetry: no body/header capture; GenAI content capture off.
- Metric tags: `model` only after allowlist resolution; no key or org tags (per-org numbers live in usage data).
- No `HeapDumpOnOutOfMemoryError`; actuator stays health + prometheus.
- vLLM: request/output logging stays off (`--enable-log-requests`, `--enable-log-outputs` not set), no DEBUG logging. On a rented host or a notebook platform the engine's stdout is the provider's log.
- **Check (smoke.sh):** send `CANARY-<uuid>` in a streamed chat, a plain chat, malformed JSON, an over-context prompt, an aborted stream, and as `?api_key=cmn_test_…CANARY`; then `docker compose logs`, `pg_dumpall` (and `modal app logs` on Modal) must contain no `CANARY`, no test-key secret and no `Bearer `.

**Access log** (Marco Civil da Internet art. 15): timestamp, IP, org, key, request id, status; 6-month retention; restricted access; separate from usage events, which stay IP-free.

**Abuse.** No public signup (BE-03: `POST /auth/register` is a 403 `registration_closed`; the operator provisions a verified account, BE-10, once the customer signed the pilot contract); trial capacity is one global cap. Signals without content: per org/key requests, tokens, 4xx/429/5xx, distinct IPs per key. Suspension: the operator sets the organization `suspended` (`PUT /organizations/{id}/admin`), auth-service deletes its `apikey:*` entries before and after the commit, and the 403 follows at once (the 60 s cache TTL bounds it only when that deletion fails, and the operator is told with a 503 `cache_eviction_failed`); running streams finish. The AUP bans illegal use, CSAM, sexualized minors, non-consensual intimate content, malware and — during the prototype — any personal data; abuse@ is published. Credible CSAM report: suspend, preserve ids/timestamps/IPs, report to the authorities (Polícia Federal / SaferNet) as Lei 15.211/2025 art. 27 requires.

**Liability.** The STF's 2025–2026 Marco Civil ruling keeps the court-order regime of art. 19 for providers that don't interfere in the flow of content; a B2B API that publishes nothing likely qualifies. Keep the notice channel and published rules anyway; confirm with counsel.

**International transfer.** None while data is synthetic. Real data abroad → ANPD standard contractual clauses (Res. CD/ANPD 19/2024, verbatim) plus the provider's DPA as sub-operator — or GPUs in Brazil. A rented GPU host abroad is exactly this transfer (every prompt crosses the border), and the foreign-GPU tax question goes to the accountant before any foreign GPU contract (D-38); "served in Brazil" is claimed only if the GPU really is there. Pinning a Modal region is not enough: logs, images and volumes stay in the US (fine only because our logs carry no content).

**Prototype = local and synthetic only.** It runs on the developer laptop with `cmn_test_` keys; nothing is exposed beyond `localhost`. When a shared or production environment exists: separate database and Valkey, production rejects `cmn_test_` keys (built: the profile `prod`, BE-04) and refuses to start if an upstream host isn't on its approved list, non-production `/v1` responses carry `X-Carmonai-Environment`, console banner.

**Erasure and export, store by store (as built, 2026-10-15).** `accounts.account` (name, email, password hash): erased by `DELETE /accounts/{id}`, exported by `GET /accounts/{id}/export`; an account never verified is erased by the daily sweep after 7 days (BE-20), with its links. `accounts.account_token` (reset and verification links, hashed): leaves with the account (cascade) and expires; expired links are swept. `accounts.terms_acceptance`: kept after erasure (account id, document, version, time, channel; no name or email) as evidence, pending counsel (BUS-10); exported under `acceptances`. `organizations.membership` (account id, role): removed on erasure, in organization id order, and refused with 409 `last_owner` while the account is the sole owner of an open organization; exported with the role. Sessions (`auth`): ended on erasure (`DELETE /auth/sessions/accounts/{idAccount}`). Batch files and objects: deleted when their organization closes (a sweep, every minute) and after `file-retention`. Usage events (ids and counts): 90 days. The ledger: append-only, ids, amounts and an operator reference that must never hold a payer's name (kept for tax records). The access log (client IP, ids): 184 days, kept by legal duty past an erasure. Valkey: `apikey:{hash}` 60 s, `rl:gw:anonymous:<ip>` 120 s, leases (ids) one ttl, the usage stream until stored; nothing there is personal data except the IP of the anonymous bucket. Prompts and answers of synchronous requests are stored nowhere; the batch files and lines above are the one exception.

**Model license.** Qwen3-4B-Instruct-2507 is Apache-2.0 without a NOTICE file; serving it over an API isn't redistribution. Record license and origin on `Model`; use "Qwen" only to describe origin.

**Regulation to watch.** PL 2338/2023 is in the Chamber's special committee, vote expected after the October 2026 elections; under the Senate text Carmonai would be a distributor, with generative-AI duties on the model developer unless we fine-tune or brand a model. ANPD generative-AI work (Radar Tecnológico 2024, Nota Técnica 1/2026).

**Before real customer data reaches any GPU:**
- [ ] Paid plan with the provider (free tiers: Modal "as-is", Lightning needs written consent for commercial use, Kaggle never).
- [ ] Provider DPA as sub-operator, named in our DPA.
- [ ] Abroad: ANPD SCCs and disclosure; otherwise a GPU in Brazil.
- [ ] Canary check passes on that provider, including its log store.
- [ ] Customer DPA and AUP signed; ROPA done; encarregado named (or a contact channel if a small agent); incident runbook written.
- [ ] Access log running with 6-month retention; suspension proven to reach the gateway within the cache TTL.

## 12. Decisions

**Made**:
- Product: OpenAI-compatible `/v1`; vLLM; tiers trial/standard/enterprise, no free tier; Batch API in phase 6; `service_tier: "flex"` at batch prices on spare capacity (2026-10-04); prepaid credits (Pix when the first customer pays).
- Billing rules: cancelled streams billed input + generated output; cancelled non-stream requests billed estimated input only; `status=error` (our failure) not billed; balance floor 0.
- Identity: refresh token in an HttpOnly cookie; sessions idle 7 days, absolute 30 days; console SPA on the same origin as the console API; explicit org creation; membership checks via organization-service; erasing the sole owner of an active org → 409 until the org is closed; `cmn_live_` keys in production and `cmn_test_` elsewhere (BE-04); public registration closed, the operator provisions verified accounts (D-04, BE-03, BE-10).
- API keys (2026-10-05): a key may expire (`expires_at` null = never; no maximum lifetime), expired and revoked keys are both 401 `invalid_api_key` and nothing else, the 50-key cap counts live keys only, and rotation is one call that issues the new key and revokes the old one in one transaction, keeping the old key's expiry. **Two gateway changes were pending and are built** (the `api-keys` route takes `/rotate`, and `ApiKeyAuthenticationManager` carries `expiresAt` in its cached `Lookup` and refuses an expired key), both in `api/gateway-service`; the text of each stays as the design record:
  1. `application.yaml`: the `api-keys` route's `Path` predicate is `/organizations/{organization}/api-keys,/organizations/{organization}/api-keys/{id}`, which does not match a third segment, so `POST /organizations/{organization}/api-keys/{id}/rotate` is a **404 at the gateway** today (measured, not inferred). Add `/organizations/{organization}/api-keys/{id}/rotate` to that list.
  2. `ApiKeyAuthenticationManager`: `Lookup` gains `Instant expiresAt`, `cacheValue()` appends `String.valueOf(expiresAt)` (ISO-8601, the fifth space-separated field), and `authentication(String)` refuses an expired one — `fields.length > 4 && !"null".equals(fields[4]) && Instant.parse(fields[4]).isBefore(Instant.now())` → `BadCredentialsException`, the same 401 `invalid_api_key` the cache's `none` gives. Measured without it: a key that expired 20 s ago still answered 200 through the gateway while auth-service's own lookup already answered 404. Without it an expired key lives up to 60 s past its expiry (the cache TTL).

- Money and usage are readable by any member of the organization, one organization per request, never "my balance" by ambient identity and never a list: `id-account` is checked against organization-service's membership and a missing header is refused (fail closed). A cost shown to a customer comes from billing-service's price table, never from a second one or a hard-coded rate, and the arithmetic that turns tokens into micro-BRL is the library's `Price.cost`, one implementation for the debit job and the summary (2026-10-05).
- Engineering: Java 25 LTS; one repo per module (CI needs a read token for the sibling repos); Kafka only when an event gets a second consumer.
- Prototype: local only on the developer laptop (RTX 3050 6 GB as the ground truth, the simulated engine for development and CI; there is no CPU engine), synthetic data, no outside users, no legal entity yet.
- Pass 2 (2026-10-07, the grilling outcome and ADRs 0001 and 0002): slot leases in Valkey and not an external router; with Valkey down each replica admits against `slots / expected-replicas`; no reserved capacity per organization; overshoot accepted and published as lag gauges; batch files in S3-compatible storage, 7 days by default and 30 at most; no CPU engine, a simulated engine for development and CI; Kubernetes and autoscaling are the next pass; roles, per-key limits, audit log and SSO are in the brief and parked for the MVP (D-45).
- MVP guide (2026-10-11, the decisions this document builds on): closed, invitation-only concierge launch with manual Pix (D-01); batch built and hidden (D-05); one public alias `carmonai/chat-standard` (D-06); the engine never public, only over WireGuard (D-16, D-23); one replica of gateway and inference, deploys in an announced window, 720 s drain, no high availability (D-12, D-22); Caddy as the only published service (D-26); access logs with the real client IP kept 184 days (D-37); keys start `cmn_live_`, trial tier until the first top-up (D-40); default-deny for an unfunded organization, overshoot of about 8 minutes borne by Carmonai (D-41); refuse unsupported parameters, `GET /v1/models/{id}`, one final usage chunk, max output 4,096 (D-42); cancelled-stream accounting on real vLLM is a launch gate (D-43); enterprise features deferred (D-45); no uptime or TTFT number published (D-52).
- SEC-04, internal endpoints (BE-21 item 8, 2026-10-15): they no longer rest on "no gateway route" and the network alone. The network split stays, as three Compose networks: `edge` (Caddy and the gateway only), `backend` (the services, the database, Valkey, Prometheus) and `observability` (Grafana and Prometheus), so that Grafana cannot reach `billing:8080`; HOST-06 builds it and the harness compose still has one `internal` network. The internal shared secret is **no longer deferred**: it is built (BE-24, header `X-Internal-Token`), ahead of gate G2, as the lock that holds when the network does not (each service listens on 8080 and 8081 in one container, so the split alone does not stop Prometheus from reaching `billing:8080/billing/grants`). Mutual TLS between services stays later.
- DB-01, database roles (BE-21 item 8, 2026-10-15): per-schema roles come later; the stack uses one superuser role at launch (`DB_USER`). The append-only ledger and price table stay enforced by triggers, not by a role (the phase-4 deviation stands).

## 13. Backlog

- [ ] **`last_used_at` on API keys** (for the console; noted 2026-10-05 with the key lifecycle work; deferred for the MVP, D-45). It is how a customer knows a key is safe to delete, but it needs a write on the request path (the gateway, per request) or a throttled writer fed by usage events — a latency/throughput decision worth making on purpose. `UsageEvent` already carries `api_key_id`, so the throttled-writer version needs no new data.
